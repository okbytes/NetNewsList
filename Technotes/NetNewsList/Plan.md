# NetNewsList: Migration Plan

This is the roadmap for turning this NetNewsWire fork into NetNewsList, a personal, iCloud-only, offline-first reading list. It is written for the one developer who owns the fork. Every file:line reference below was checked against the repository at the time of writing; when a line number drifts, the surrounding function name is given so it can be found again.

> **Status (2026-10-01).** PR1–PR12 and follow-up 1 (Safari capture) are done and on `main` (they were built on a `netnewslist` branch, retired 2026-10-09), built and unit-tested on both platforms but not yet tried on devices. What each PR changed, and how it differed from this plan, is in the **Progress** notes at the end of section 5; the last one, "merge and wrap-up", lists what is still open. The user's own to-dos are in `TODO-Brett.md`; how the finished app works is in `ReadingList.md`.

## 1. Summary

**What NetNewsList is.** A manually curated reading list with the NetNewsWire three-pane UX (sidebar, timeline, detail), article rendering and themes, keyboard navigation, read/unread, starred and full-text search. Articles are added by URL from the share sheet (Mac and iOS), a Chrome extension (Mac), a `netnewslist://add` URL scheme, paste, and Shortcuts. At save time the app fetches the page, extracts the readable body and stores it, so the article is readable offline on the iPhone and survives the page disappearing. The only store and sync mechanism is the user's private CloudKit database. No third-party servers, no RSS.

**Architecture in one paragraph.** The existing iCloud account (`CloudKitAccountDelegate` + `CloudKitArticlesZone` + `Modules/CloudKitSync` + `Modules/SyncDatabase`) already moves a starred article's full content from the Mac to the iPhone and renders it offline from SQLite. NetNewsList keeps that path and turns it into the whole app: exactly one `.cloudKit` account, exactly one synthetic `Feed` (`netnewslist://reading-list`) so that `articles.feedID NOT NULL` and every smart-feed query keep working, canonical-URL `uniqueID`s so that both devices compute the same `articleID`, `read` reinterpreted as Archive, one new sync-status key (`.content`) so that a body extracted after the first upload actually reaches the server, and roughly fourteen conditions flipped or deleted so that content is always uploaded and never pruned. Extraction is a new ~500-line module: a `URLSession` fetch, a hidden `WKWebView` that loads the fetched HTML with page JavaScript disabled and runs vendored Readability.js plus DOMPurify, and the result written into `Article.contentHTML`, which the renderer, all eight themes and FTS4 search already consume. Everything feed-shaped (four sync services, the local RSS refresher, FeedFinder, Secrets, OPML, AppleScript, the Safari App Extension, account preferences, folders, drag and drop) is deleted. The sidebar becomes four fixed lists: Inbox, Starred, Archive, All.

**Should this app do the scraping?** Yes, but only a small, bounded amount, and only in the main app. With zero servers the readable body can be produced in exactly two places: the browser at capture time, or the app. Storing only the URL fails both hard requirements (offline, survives deletion), and there is no public Apple Reader API. Extensions cannot do it (the iOS share extension has a ~120 MB cap and no background time; neither extension has a CloudKit entitlement). So the app performs one HTTP GET and one Readability pass per saved URL, at save time, and nothing else: no polling, no crawling, no per-site rules, no retry-forever. Failure is a visible state with a Retry command. Safari shares can optionally pre-extract inside the live page via `Shared/ShareExtension/SafariExt.js` (which today returns only `document.URL`), and a Shortcut using Apple's "Get Article using Safari Reader" action can pass a body to the App Intent. Both are optional later additions, not the backbone. The current `Shared/Article Extractor/ArticleExtractor.swift` (Feedbin Mercury client, `SecretKey.mercuryClientID`/`Secret` at :39-42) is stubbed in PR5 and deleted with its ~12 dependents in PR7.

## 2. Decisions

All decisions below were confirmed on 2026-09-28. D1, D3 and D6 were the ones held for confirmation; the answers are recorded in each.

### D1. Sync engine: adapt the existing CloudKit path; keep both zones for v1 **[confirmed]**

**Confirmed 2026-09-28.** Adapt first and judge it in practice; if adaptation proves poor, replace the store behind `ReadingListStore` with a CKSyncEngine implementation (optional follow-up 3). There is exactly one built-in iCloud account and no other account types until one is clearly needed. The Account *zone* is an internal CloudKit storage area, not a user account; it holds only the Reading List feed record and stays in v1.

**Decision.** Keep `Modules/CloudKitSync`, `Modules/SyncDatabase` and `Modules/Account/Sources/Account/CloudKit`. Flip the content-gating rules (section 4) so every article uploads status plus content and nothing prunes content, and add one sync-status key so content written after the first upload is sent as a modification rather than a `saveIfNew` (C0 in section 4; this is the one thing the existing path cannot do today). Keep the Account zone in v1: it is what makes the synthetic feed converge across two devices (deterministic record name `url.md5String`, CloudKitAccountZone.swift:95, plus dedupe in `createFeedIfNecessary`, CloudKitAccountZoneDelegate.swift:182-185), and `accountDidInitialize` keys first-run setup on `account.externalID == nil` (CloudKitAccountDelegate.swift:686-701), which the Account zone supplies. Route all reading-list writes through one file inside the Account module, `Modules/Account/Sources/Account/Account+ReadingList.swift`, whose members are `public` and are the only reading-list API the app targets see; a small `ReadingListStore` protocol (also public, in the same module) is declared over exactly those members so a future CKSyncEngine store is a swap rather than a second UI cut-over. It has to live inside the module: `Account.updateAsync(feedID:parsedItems:deleteOlder:)`, `Account.delete(articleIDs:)` (Account.swift:1034, no `public`), `Account.delegate` (typed `AccountDelegate`, :246) and `flattenedFeedsIDs` (private, :252-254) are all internal or private, and `storeArticleChanges(new:updated:deleted:)` exists only on `CloudKitAccountDelegate` (:1102), not on the `AccountDelegate` protocol, so the extension does `guard let delegate = delegate as? CloudKitAccountDelegate` (or the method is added to the protocol).

**Why.** The inbound path (Article record -> `ParsedItem` -> `updateAsync(feedID:parsedItems:deleteOlder: false)`, CloudKitArticlesZoneDelegate.swift:106) already works. Making it work for every article is about a dozen small edits plus deleting ~450 lines whose only job is to remove content. That yields a two-device, title-only sync checkpoint with roughly 200 changed lines, days into the project, while the UI's dependency on `Account`/`AccountManager` (122 importing files, 163 `AccountManager.shared` call sites) stays untouched.

**Rejected.** A new CKSyncEngine store (Proposals 2 and 4): a cleaner end state (one record type, no flipped RSS conditions, no hand-rolled change tokens) but it deletes ~4,700 lines, writes 500-1,400 new ones, and produces no cross-device test until roughly the third week; its cut-over PR changes ~55 files under warnings-as-errors and Swift 6.2 strict concurrency with nothing running until everything compiles. Deleting the Account zone now (Proposal 3): `addDeadFeed` calls `accountZone.createFeed` (CloudKitAccountDelegate.swift:1053-1057), `accountDidInitialize` sets its delegate, `performRefreshAll` fetches it (:887), and the folder/rename/move/remove `AccountDelegate` methods route through it, so removal is a rewrite plus a stubbing pass, not a rename. It is a fine optional follow-up after the two-device checkpoint passes.

### D2. Data model: one synthetic Feed, canonical-URL uniqueID, nil dates, Archive = read, hard delete

**Decision.**
- One permanent `Feed`, name "Reading List", `url == feedID == "netnewslist://reading-list"`, `externalID` = the deterministic Account-zone record name (`url.md5String`). It is created by a new `ensureReadingListFeed()` in `Account+ReadingList.swift` that calls `existingFeed(withURL:)` (Container.swift:38, implemented at :110; `Account` conforms to `Container`) and otherwise inserts the feed into the OPML tree and calls `accountZone.createFeed`. Today's `createFeed(url:name:container:validateFeed: false)` does **not** go straight to `addDeadFeed`: `createRSSFeed` (CloudKitAccountDelegate.swift:938-958) runs `FeedFinder.find(url:)` first (:946), does `syncProgress.addTasks(5)` bookkeeping (:943) and reaches `addDeadFeed` (:1043-1067) only in the not-found branch; PR5 rewrites it so that `addDeadFeed` is the whole path, drops the progress bookkeeping, treats `serverRecordChanged` from `accountZone.createFeed` as "already exists" (adopt the record) and never removes the feed from the tree on failure (today's :1060-1065 does). The non-http scheme guarantees `Downloader` returns an empty response without error if anything ever tries to refresh it. Treat the URL string as immutable: changing it changes every `articleID`.
- `uniqueID` = canonical URL: lowercase scheme and host, fragment stripped, `utm_*`/`fbclid`/`gclid` query items removed, trailing slash normalized. `articleID = md5("\(feedID) \(uniqueID)")` (Article.swift:56-58) is therefore identical on both devices; re-saving a page goes through `findAndSaveUpdatedArticles` and refreshes the body while preserving read/starred.
- Save with `datePublished = nil` and `dateModified = nil`. `logicalDatePublished = datePublished ?? dateModified ?? status.dateArrived` (ArticleUtilities.swift:87-88) then equals the save time everywhere: the existing `.date` sort key becomes date-saved without a new `ArticleSortKey` case (the enum is `String`-backed and persisted in prefs, Shared/Timeline/ArticleSortParameters.swift:12-17; only relabel it "Date Saved"), the limited fetches' `coalesce(datePublished, dateModified, dateArrived)` ordering agrees (ArticlesTable.swift:803), the Today query's `datePublished is null and dateArrived > ?` branch (ArticlesTable.swift:710) becomes "saved in the last 24 h" for free, and the 183-day read-on-insert rule can never fire. The page's own publication date, when Readability finds one, goes into the stored HTML header, never into `datePublished`.
- Extraction state is derived, no schema change: `contentHTML == nil` means pending. This syncs for free, so a device that receives a pending record can extract it itself. A small local-only JSON ledger (attempts, last error, per account data folder) drives the "Failed" glyph and backoff. Who extracts: the saving device, immediately, and any device that receives a record from CloudKit that is still pending when it looks (on launch, on foreground, after a fetch) and whose local ledger shows fewer than three attempts. There is no waiting period: a record written by the remote browser extension (D4) has no saving device, and a device cannot tell that case from "my other device saved this a moment ago", so the receiving device just does the work. Extraction is idempotent, so a double extraction is harmless: both devices write the same body through `.all` (last writer wins), and in practice the saving device's body usually lands before the other device opens the app, at which point the record is no longer pending.
- Archive = `read`, Inbox = `unread`. `MarkStatusCommand -> Account.markArticles -> updateStatusesAsync -> SyncDatabase -> CloudKitSendStatusOperation -> badge` works unchanged; only labels change.
- Delete is explicit and hard, and removes both rows. `ArticlesTable.delete(articleIDs:)` (:345) calls `removeArticles` (:1038), which deletes only from `articles`; the `statuses` row survives until `deleteOldStatuses` (:590-607) sweeps it after 30 days, and starred orphans are never swept. That would make "delete then re-save" inherit old read/starred flags and the old `dateArrived` depending on elapsed time, so the delete path gains a status-row delete in the same transaction. `deleteArticles(articleIDs:)` in `Account+ReadingList.swift`: `storeArticleChanges(deleted:)` then `database.deleteAsync(articleIDs:)`, then `updateUnreadCounts(feeds: [readingListFeed])` and post `.AccountDidDownloadArticles` with `userInfo[feeds] = Set<Feed>([readingListFeed])`. Both are required: `sendNotificationAbout` (Account.swift:1523-1560) builds its `feeds` set only from new/updated articles, and both timeline handlers return early unless `userInfo[feeds]` is a `Set<Feed>` (TimelineViewController.swift:732-734, SceneCoordinator.swift:663-665); without the unread-count call the Inbox badge goes stale after deleting an unread item. The `.delete` case in `modifyArticles` removes the status record, the `.deleteSelf` reference removes the content record, and the other device's `CloudKitArticlesZoneDelegate.delete(recordKeys:)` (:69-79) calls `account.delete(articleIDs:)`, which now removes both rows there too. `deleteOldStatuses` is kept: after PR5 the only orphan statuses are rows from a remote status arriving before its Article record or after a remote delete, invisible through the natural join and harmless to sweep.

**Rejected.** One Feed per host (free favicons, but a mutable synced tree and races again). Removing Feed from Article (schema, CloudKit and 100+ UI sites). UUID uniqueIDs (no duplicate detection). Storing the site host in `feedID` (a reuse hack a future reader will misread). A third `archived` flag (new column, record field, command case and UI for nothing). A new `ArticleSorter.dateSaved` key (migration surface for a value `.date` already produces).

### D3. Extraction: hidden WKWebView + Readability.js + DOMPurify, static HTML with page JS off **[confirmed]**

**Confirmed 2026-09-28.** WKWebView is the on-device equivalent of a headless browser; Playwright-style headless Chromium cannot ship inside an iOS app.

**Decision.** One engine in v1, in a new `Modules/Extraction` local package (its own `swiftSettings`, so app-level warnings-as-errors does not apply to vendored JS glue):
- `PageFetcher`: a ~60-line `URLSession` wrapper. Browser UA, 20 s timeout, redirects followed, 5 MB cap, `text/html` only, returns final URL and HTML. `UserAgent.browserUserAgent` (Modules/RSWeb/Sources/RSWeb/UserAgent.swift:31) is a `@MainActor static var` populated by `WebViewConfiguration.resolveBrowserUserAgent()` at launch (Mac/AppDelegate.swift:165, iOS/AppDelegate.swift:63), so the coordinator copies it on the main actor and hands the string to the fetcher. `Mac/Resources/Info.plist:55-58` (`NSAllowsArbitraryLoads`) must survive the identity cleanup or `http://` pages fail to fetch. **Never** use RSWeb `Downloader` for this: it is `@MainActor` (Downloader.swift:18), one connection per host (:31), sets no explicit timeout (URLSession's 60 s default applies, :25-31), and caches any response without a transport error, including HTTP 403/404/429 bodies, for 180 s (Downloader.swift:117-120, DownloadCache.swift:25), so Retry would return the cached failure.
- `ReadabilityWebExtractor`: hidden `WKWebView` built from a copy of `WebViewConfiguration.configuration(with:)` (Shared/Article Rendering/WebViewConfiguration.swift; non-persistent store at :33, scheme handler at :37, content rule list at :111, user scripts at :138). `configuration.defaultWebpagePreferences.allowsContentJavaScript = false` is set on the configuration itself (not only in a navigation-delegate `decidePolicyFor`), so page scripts never execute for `loadHTMLString(html, baseURL: finalURL)` while `evaluateJavaScript` and user scripts still run the injected Readability.js 0.6.0 + DOMPurify + a small glue script returning `{title, byline, content, excerpt, siteName, lang, publishedTime, leadImage}`. The web view is attached to the key window at zero size and alpha 0 (a view outside the window hierarchy may be throttled, and on iOS it must be in a window at all). Serial queue, one web view, 20 s hard timeout, foreground only (WKWebView JS is suspended in the background). Confirm the "JS off for page, on for evaluateJavaScript" behaviour on macOS 15 and iOS 17 with a one-file spike before PR7 starts.
- Escalation, manual only in v1: a "Retry with live page" command loads the live URL in the same hidden web view with JS on and content rules attached, for SPAs and consent walls. Reset to pending on `resignActive`.
- Fallback order once everything exists: body supplied by the caller (Shortcut or SafariExt.js) -> static extraction -> live-page retry -> title + URL "Failed" with Retry.
- Output passes through DOMPurify and lands in `Article.contentHTML`. Content JavaScript for the detail web views is **user-gated today, not off**: `WebViewConfiguration.allowsContentJavaScript(for:)` (:53-61) returns `false` only when `AppDefaults.shared.isArticleContentJavascriptEnabled` is off, otherwise `true` unless the slashdot special case applies, and both detail controllers apply it per navigation (DetailWebViewController.swift:243, WebViewController.swift:452), with a live switch on both platforms (Mac/Preferences/General/Base.lproj/GeneralPreferencesView.xib:114; iOS/Settings/SettingsViewController.swift:134, :408). Stored extracted HTML is untrusted, so PR7 makes the stored-content render path ignore the preference (hard `false`) and keeps the preference only for the Show Original live load; the switch is relabeled accordingly. Keep the `ContentRules.json` blocker and the non-persistent rendering store.
- Offline images: dated to PR11, per-device. Each device downloads its own images on first online sync; no CKAsset for images in v1 (details in section 3).
- The Reader View toggle becomes **Show Original**: stored content is the default; the toggle loads the live URL in the detail web view (online only). `DetailState.extracted`, `ArticleExtractor`, `ExtractedArticle`, `isShowingExtractedArticle` restoration and the reads of `Feed.readerViewAlwaysEnabled` are deleted in PR7; the `Feed.readerViewAlwaysEnabled` property itself (Feed.swift:147-153, FeedSettings.swift, FeedSettingsDatabase.swift:25, FeedSettingsImporter.swift, DataExtensions.swift:29, FeedSettingsImporterTests.swift) stays until PR10 because both Feed inspectors (Mac/Inspector/FeedInspectorViewController.swift, iOS/Inspector/FeedInspectorViewController.swift) and `SidebarViewController+ContextualMenus.swift:141, :239` read it and are deleted in PR9/PR10.

**Rejected.** Mercury/Feedbin (private keys, stale). Pure-Swift `swift-readability` on SwiftSoup master as the primary engine (Proposal 3): the only engine that runs in the background, but it fails on SPAs, consent walls and logged-in pages, and it means owning ~3,000 vendored lines plus a hand-written allowlist sanitizer; adopt later only if background extraction is actually missed. Three engines with leases and a conflict resolver (Proposal 4): far past diminishing returns for one user. Extraction inside an extension (memory, no time). Defuddle (young API).

### D4. Ingress v1: one app-group queue, many doors

**Decision.** Make the app-group request file the single ingestion API; extraction happens only in the main app.
- `ExtensionFeedAddRequest {name?, feedURL, destinationContainerID}` becomes `SavedArticleRequest {url, title?, body?}`; `ExtensionFeedAddRequestFile.processRequest` (Shared/ShareExtension/ExtensionFeedAddRequestFile.swift:163-188) calls the save path instead of `createFeed`. `ExtensionContainers`, `ExtensionContainersFile`, `ShareDefaultContainer` and the iOS folder picker are deleted. Move to one file per request under `<group>/Inbox/<uuid>.plist` when bodies start flowing through it (SafariExt.js capture), because a read-modify-write of one shared plist is the wrong shape for 200 KB payloads. `ExtensionFeedAddRequestFile.filePath` (:19-23) force-unwraps the `AppGroup` Info.plist key and `containerURL(forSecurityApplicationGroupIdentifier:)`, so any mismatch between the group in the entitlements and the string in Mac/Resources/Info.plist:5-6 or Mac/ShareExtension/Info.plist:7-8 is a launch crash; replace both force-unwraps with a guard that logs and disables ingress.
- Share extensions on both platforms keep their URL resolution (JS preprocessing dictionary, `UTType.url`, plain text; iOS/ShareExtension/ShareViewController.swift:203-215) and just enqueue.
- App Intent: move `iOS/AppIntents/AddFeedAppIntent.swift` and `iOS/AppIntents/NetNewsWireAppShortcuts.swift` (the `AppShortcutsProvider` whose phrases reference `AddFeedAppIntent`, :11-16) to `Shared/AppIntents/` as `SaveArticleIntent` + `NetNewsListAppShortcuts`, add both to the Mac target so Siri and Spotlight phrases exist on both platforms, keep `openAppWhenRun = false` (:19), drop the account/folder parameters (:24-27), add an optional `body` parameter so a Shortcut using "Get Article using Safari Reader" can deliver Safari's own extraction.
- `netnewslist://add?url=&title=`: on the Mac, a new ~40-line `Mac/AppDelegate+URLHandling.swift` keeps the kAEGetURL registration and theme branch from Mac/Scripting/AppDelegate+Scriptability.swift:46-67 and inserts the `add` branch **before** the fall-through at :76-83 (which today normalizes any other string and calls `addFeed`). On iOS, insert before the theme guard in `SceneDelegate.scene(_:openURLContexts:)` (iOS/SceneDelegate.swift:202-213), delete the `feed:`/`feeds:` branch (:130-137) and **keep** the widget deep-link branches (:139-193, matched by `contains` on `nnw://showunread` etc.). Register `netnewslist` in both Info.plists (iOS/Resources/Info.plist:36-50; Mac/Resources/Info.plist:36) and drop `feed`, `feeds`, `x-netnewswire-feed`, `netnewswire`; fix the `CFBundleURLName` values (`com.ranchero.NetNewsWire-Evergreen.iOS(.feed)` at iOS/Resources/Info.plist:34-35, :45-46; "RSS Feed" at Mac/Resources/Info.plist:34-35). Between PR3 and PR8 the Mac has no URL-scheme ingress (only the theme branch), which is fine.
- Chrome (and any Chromium such as Helium): one MV3 extension in `chrome-extension/` with two modes, chosen in its options page.
  - **Local mode**, for a machine that has the Mac app: the toolbar click (a user gesture) does `chrome.tabs.update(tab.id, {url: "netnewslist://add?url=..."})`. One "Always allow" prompt, ~40 lines.
  - **Remote mode**, for a machine that does not have the app and cannot sign the OS into your Apple ID (a managed work computer): the extension writes the article straight into your private CloudKit database as a **pending** record pair, using CloudKit Web Services with an Apple ID web sign-in that lives only in the browser. Your Mac or iPhone receives the record through the normal inbound path, sees `contentHTML == nil`, and extracts it (D2). This is the asynchronous form of the same save: the record the extension writes is exactly what `saveArticle` writes before extraction. Details in section 3.4; delivered as PR8b.
  Do not use the CloudKit JS library for remote mode: MV3 forbids remotely hosted code, the library's sign-in button and popup do not fit an extension, and the REST surface needed here is two requests. Talk to `https://api.apple-cloudkit.com/database/1/<container>/<environment>/private/...` directly.
- Paste: the Add Article sheet prefills from the pasteboard (Mac Cmd-N, iOS add button); URL drop on the Mac sidebar/timeline.
- Delete: the Safari App Extension target "Subscribe to Feed" (pbxproj target 6581C73220CED60000F4AD34), `Mac/Scripting/` except the GetURL handler, `Mac/Resources/NetNewsWire.sdef`, `Mac/Resources/Info.plist:62-63` (`NSAppleScriptEnabled`) and :74-75 (`OSAScriptingDefinition`), and `Mac/AppDefaults.subscribeToFeedsInDefaultBrowser` (the app-group suite for the Safari extension, Mac/AppDefaults.swift:36, :126-131).
- Optional later: Readability.js + DOMPurify inside `SafariExt.js` returning `body` (capture-time, logged-in, paywall-aware, Safari only).

## 3. Target architecture

### 3.1 Data model and storage

**Local schema.** Unchanged. `articles (articleID PK, feedID NOT NULL, uniqueID, title, contentHTML, contentText, markdown, url, externalURL, summary, imageURL, bannerImageURL, datePublished, dateModified, searchRowID, authors)` natural-joined with `statuses (articleID, read, starred, dateArrived)` (ArticlesDatabase.swift:434-437). Rules that must hold forever: never add a same-named column to both tables (every query is `articles natural join statuses`); new columns go on `articles` via the guarded `ALTER TABLE` pattern at :76-84; do not create a `tags` table.

Column meanings for NetNewsList:
- `feedID` = `"netnewslist://reading-list"` for every row.
- `uniqueID` = canonical URL; `url` = canonical URL; `externalURL` = final URL after redirects if different.
- `title`, `contentHTML` (sanitized extracted body or nil = pending), `summary` (Readability excerpt), `imageURL` (lead image), `authors` (byline), `datePublished`/`dateModified` = nil.
- `statuses.read` = archived; `statuses.starred`; `statuses.dateArrived` = date saved.

**Sync-status keys.** `SyncStatus.Key` (Modules/SyncDatabase/Sources/SyncDatabase/SyncStatus.swift:14-18: `read`, `starred`, `deleted`, `new`) gains **`content`**: "the local body changed, re-upload the content record". `CloudKitArticleStatusUpdate.record` then classifies: any `.deleted` -> `.delete`; exactly one status and it is `.new` -> `.new` (first upload, `saveIfNew`, idempotent when both devices save the same URL); any `.new` or `.content` among several -> `.all` (`modify` with `.changedKeys`, which overwrites the server record); otherwise `.statusOnly`. See C0 in section 4.

**CloudKit record layout.** Unchanged from today, one container `iCloud.$(ORG).NetNewsList`, private database, two zones:
- Zone `Account`: `AccountWebFeed` record for the single reading-list feed (record name `md5(url)`), plus the account record. Nothing else ever lands here.
- Zone `Articles`: `ArticleStatus` record `s|<articleID>` with `webFeedExternalID`, `read`, `starred` (strings "0"/"1"); `Article` record `a|<articleID>` with `webFeedURL` (must equal the feed's `feedID`), `uniqueID`, `title`, `contentHTMLData` (LZFSE), `contentTextData`, `url`, `externalURL`, `summary`, `imageURL`, `datePublished`, `dateModified`, `parsedAuthors`, and a `.deleteSelf` reference to the status record. New in PR6: an optional `contentHTMLAsset` (CKAsset) used only when the compressed body exceeds ~700 KB; `makeParsedItem` (CloudKitArticlesZoneDelegate.swift:122-178) reads either.

Merge semantics stay what they are: per-record last writer wins on CloudKit, with the existing `pendingReadStatusArticleIDs`/`pendingStarredStatusArticleIDs` guards (CloudKitArticlesZoneDelegate.swift:81-92) protecting local unsent status flips. Deletes are hard and win. Do not add leases or per-field timestamps unless a real conflict is ever observed.

**Change tokens and cleanup dates** live in `UserDefaults.standard` (`cloudkit.server.token.<zone>.<owner>`, CloudKitZone.swift:95-100; `cloudkit.lastCleanUpDate`, CloudKitAccountDelegate.swift:1193) and survive account deletion and database wipes; `accountWillBeDeleted` (:705-710) resets them only when the account is removed through the account UI. This matters twice: between PR4 and PR5 (delete the apps, not just the account, before wiping the Development environment, or stale tokens produce `changeTokenExpired`/`zoneNotFound` loops) and in the "Reset iCloud Sync" command (section 3.2).

### 3.2 The save/extract/sync/render pipeline

```
URL (share ext / intent / scheme / paste / Chrome)
  -> SavedArticleRequest in the app-group queue (or direct call when the app is frontmost)
  -> Account.saveArticle(url:title:extracted:)   [Account+ReadingList.swift, public]
       URLCanonicalizer -> ParsedItem (feedURL == feedID, uniqueID == canonical URL, dates nil)
       -> updateAsync(feedID:parsedItems:deleteOlder: false)   posts .AccountDidDownloadArticles
       -> delegate.storeArticleChanges(new:) -> SyncDatabase row .new
       -> kick: lastNoChangeSyncDate = nil, post .AccountDidQueueArticleStatuses, sendArticleStatus() now
  -> ExtractionCoordinator (main app, foreground): PageFetcher -> ReadabilityWebExtractor -> DOMPurify
       -> Account.updateArticleContent(articleID:extracted:)  (same updateAsync path; body now present)
       -> storeArticleChanges(updated:) -> SyncDatabase row .content -> record == .all -> modify(.changedKeys)
       -> same kick as above
  -> other device: silent push / BGAppRefreshTask / foreground fetch -> CloudKitArticlesZoneDelegate
       -> ParsedItem -> updateAsync(deleteOlder: false) -> SQLite
       -> if contentHTML == nil: ExtractionCoordinator extracts here too (the record may have come from the remote browser extension, which never extracts)

  Remote browser extension (no app on that machine): Apple ID web sign-in -> CloudKit Web Services `records/modify`
       -> writes s|<articleID> + a|<articleID> with no content -> same inbound path as above on every device
  -> ArticleRenderer (unchanged): body = contentHTML ?? contentText ?? summary, baseURL = link
  -> WKWebView, content JS off for stored content, nnlasset:// scheme handler for offline images (PR11)
```

**The kick is not optional.** `syncArticleStatus` returns early while `lastNoChangeSyncDate` is within `noChangeBackoffInterval` (30 minutes; CloudKitAccountDelegate.swift:56, :186-202), and `ArticleStatusSyncTimer` backs off from 120 s to 1800 s after an idle run (Shared/Timer/ArticleStatusSyncTimer.swift:15-16). `markArticles` already resets the backoff and posts `.AccountDidQueueArticleStatuses` (:633-636), which `ArticleStatusSyncTimer` observes to leave its idle backoff (Shared/Timer/ArticleStatusSyncTimer.swift:27, :99-105); on iOS the background-wait path `isSyncArticleStatusRunning`/`isWaitingForSyncTasks` (iOS/AppDelegate.swift:47-48, :275-350) then keeps the app alive until that send finishes, so a save made just before backgrounding gets its send. `saveArticle`, `updateArticleContent` and `deleteArticles` must do exactly the same and then call `sendArticleStatus` directly; otherwise a saved article can sit on the device for half an hour and the PR6 "appears within a minute" checkpoint depends entirely on a best-effort silent push.

**First launch and feed ordering.** `accountDidInitialize` (:646-703; first-run branch :686-701) today runs `findOrCreateAccount` inside an unstructured `Task`, sets `account.externalID`, then `initialRefreshAll`, while the subscriptions run outside the Task. PR6 rewrites it as one sequence inside the Task: (1) `findOrCreateAccount` if `externalID == nil`; (2) `ensureReadingListFeed()`, which inserts the local Feed with `externalID = url.md5String` into the tree **before any article fetch**, so that Article records arriving in the same launch resolve `article.feed` (`sendNotificationAbout` derives `feeds` from `article.feed`, and the remote-notification operation and `performRefreshAll` both fetch the Account zone first, so ordering is otherwise preserved), then calls `accountZone.createFeed` and treats `serverRecordChanged` as success; on device 2 the later Account-zone fetch dedupes by `existingFeed(withExternalID:)` (CloudKitAccountZoneDelegate.swift:182-192) against that same deterministic id; (3) `initialRefreshAll`; (4) `subscribeToZoneChangesWithActivity` for both zones unconditionally (C9). Every later launch runs (2) again as a cheap guard.

**Zone loss recovery.** `performRefreshAll` reacts to `CloudKitZoneError.userDeletedZone` by tearing down the whole feed tree (:890-895), which would remove the Reading List feed: every fetch then returns nothing (`fetchUnreadArticles` returns early on an empty feed set, ArticlesTable.swift:796-798) and, before L2 is gone, the next launch purges the database. And the error text for `CloudKitZoneError.userDeletedZone`/`.corruptAccount` (Modules/CloudKitSync CloudKitZone.swift:27-30) tells the user to remove and re-add the iCloud account, UI that PR5 deletes, while `.notAuthenticated` (CloudKitError.swift:62-63, surfaced through `iCloudAccountUnavailableError` :827-839) tells them to sign in to iCloud. PR5: replace the teardown with `resetChangeToken()` on both zones plus `ensureReadingListFeed()`; reword the three messages; add a **Reset iCloud Sync** command (Mac Preferences > iCloud, iOS Settings) that resets both tokens, clears `cloudkit.lastCleanUpDate`, re-runs the first-launch sequence and re-subscribes. This is the single account's replacement for remove-and-re-add.

Pending items (`contentHTML == nil`) are picked up by `ExtractionCoordinator.drainPending()` on launch, on foreground, and after each CloudKit fetch, subject to the "saving device first, others after 10 minutes" rule in D2. Since the Mac is usually the online device it does most of the extracting; the iPhone finishes anything it saved itself the next time it is opened. iOS saves made while the app was closed sit in the app-group queue until the next launch; the renamed `BGAppRefreshTask` drains the queue and fetches changes but does not run the WKWebView engine (JS is suspended in the background).

### 3.3 Offline images (PR11)

Per-device, no CloudKit involvement:
- After extraction, a JS pass collects `<img src>`, picks one `srcset`/`<picture>` candidate at or below ~1600 px wide, honours `data-src`/`data-lazy-src`, skips declared 1x1 pixels and `data:` URIs over 50 KB, rewrites `src` to `nnlasset://<articleID>/<sha256(originalURL)>` and keeps the original in `data-nnl-src`. `main.js convertImgSrc` leaves any `scheme://` src alone, so rewritten HTML renders untouched.
- Swift downloads with `URLSession` (browser UA, `Referer: <page URL>`, one retry without Referer on 403, 20 s timeout, 4 concurrent), caps at 40 images / 25 MB per article, downsamples to 1600 px, stores under `Application Support/NetNewsList/Articles/<articleID>/<sha>.<ext>` keyed by SHA-256. Not `Caches/`: `CacheCleaner` (Shared/Extensions/CacheCleaner.swift:28-32) purges `Caches/Images` every three days and the OS may evict Caches.
- Runs at save time and when new records arrive while the app is in the foreground.
- `ArticleAssetSchemeHandler`, cloned from `iOS/Article/ArticleIconSchemeHandler.swift` and the Mac `DetailIconSchemeHandler`, registered in `WebViewConfiguration.configuration(with:)` beside the icon scheme (:37): serve from disk; if missing and online, fetch `data-nnl-src` and backfill; if missing and offline, serve a small inline SVG placeholder. iOS tap-to-zoom reads the store for `nnlasset` URLs.
- Delete removes the article's directory. A startup orphan sweep removes directories with no article row.
- Upgrade path if two-device parity without ever being online matters: one CKAsset zip per article. Never inline data URIs (1 MB record limit).

## 8. Risks and open questions

**Risks**
1. A missed retention, gating or upload rule silently loses content. C0 is the one that would have shipped: every article uploads pending first, and without the `.content` key no body ever follows. Mitigation: all of section 4 lands in PR5 with the three regression tests (classification, planner, retention); the PR6 checkpoint includes double relaunch, a save-then-archive item and delete/re-save; the PR7 Airplane Mode check proves bodies arrived after the pending record. The weekly `shouldDeleteContentRecord` cleanup is covered by deleting the code and asserting in the planner test that no update plans a content delete; do not rely on "advance the clock a week" on devices.
2. Extraction quality and hangs. SPAs, consent walls and logged-in pages yield title-only saves in v1; WKWebView is foreground-only, so iOS saves made while closed wait for the next launch. Mitigation: the D3 spike before PR7, visible Failed state with Retry and Retry with Live Page, the App Intent `body` parameter, later SafariExt.js capture.
3. 1 MB CKRecord limit. Without C8 one huge page blocks its own save forever and the error is swallowed (:236-240). Test the asset spill with one very long page in PR7, on both write and read sides.
4. CloudKit environment mismatch. Debug against Production means schema errors; Production without a schema deploy means TestFlight fails. Verify the environment in Console on the first Debug run (PR4) and deploy in PR12.
5. Synthetic feed identity is load-bearing. Changing `netnewslist://reading-list` changes every `articleID` and re-ingests everything. Never let a refresher or FeedFinder see it. Zone loss (`userDeletedZone`) must recreate it, never tear the tree down.
6. Concurrent first launch creates the feed locally on both devices; convergence relies on the deterministic record name, `serverRecordChanged` treated as success, and externalID dedupe. Bring the second device up after the first has synced once; verify one feed in Console.
7. Silent pushes are best-effort (low priority, none after force-quit, never in the simulator), and the send side backs off for 30 minutes after a quiet sync unless the save path kicks it. Foreground fetch, Sync Now, the immediate send in `saveArticle` and the BGAppRefreshTask are the reliable paths.
8. SceneCoordinator and MainWindowController surgery can break selection and restoration invariants. Remove incrementally with device testing after each cut; keep persisted identifier strings stable.
9. Warnings-as-errors and pbxproj hygiene. Build both schemes after every PR; VerifyNoBS is Mac-only; edit exception sets when `Shared/ShareExtension` files move; keep xib selector bindings pointing at live actions.
10. Residue. The end state still rides `CloudKitZone` (UserDefaults change tokens), `SyncDatabase`, `ParsedItem` and a synthetic feed in an OPML file. `ReadingListStore` and `Account+ReadingList.swift` keep the CKSyncEngine door open; the regression tests keep the flipped conditions from being flipped back.

**Open questions**
1. Sync engine (D1): adapt now and possibly swap later, or take the CKSyncEngine rewrite up front and accept ~3 weeks before a two-device test? Recommended: adapt. **Settled:** adapt first; CKSyncEngine behind `ReadingListStore` if adaptation proves poor.
2. Extraction engine (D3): WKWebView + Readability.js in the foreground only, or vendor pure-Swift Readability to gain background extraction at the cost of owning it? Recommended: WKWebView only in v1. **Settled:** WKWebView only in v1.
3. Keep the Account zone in v1 (recommended) or delete it in PR5 as Proposal 3 suggested? **Settled:** keep; one built-in iCloud account, no other account types (YAGNI).
4. Today: delete, or keep as "Saved Today" (free with nil `datePublished`; its widget and deep links come with it)? Recommended: delete for a four-list sidebar; trivially reversible. **Settled:** delete.
5. Debug/Release coexistence: keep the `-DEBUG` bundle and group suffixes (recommended, both installed side by side, both against the Development environment while development-signed) or drop them? Answered 2026-10-12: kept; the Mac Debug build is also named NetNewsList Dev and has its own link scheme (Progress note "an installed Mac app").
