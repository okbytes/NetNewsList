# How NetNewsList works

NetNewsList is NetNewsWire with feeds replaced by saved pages. This note describes the pieces that are new or that behave differently from NetNewsWire, and the traps that cost time. `Plan.md` has the history: the decisions (D1–D7), the traps found before the work (section 4) and a progress note per PR.

## Data model

- **One account, one feed.** There is exactly one account, iCloud (`AccountManager.shared.defaultAccount`, `AccountType.cloudKit`, folder `Accounts/2_iCloud`). Every saved article belongs to one synthetic feed whose URL and feed ID are `netnewslist://reading-list` (`Account.readingListFeedURL`), created by `ensureReadingListFeed()` and never shown. Its iCloud record name is `md5(url)`, so every device creates the same feed. Never change that URL: it is part of every article ID.
- **Article identity.** `uniqueID` is the canonical URL (`URLCanonicalizer`); `articleID = md5("netnewslist://reading-list <canonical URL>")`. The same page saved on two devices, or from the browser extension, is one article. Canonical form: lowercase scheme and host, default port dropped, fragment dropped, `utm_*`, `fbclid`, `gclid`, `dclid`, `msclkid`, `mc_cid`, `mc_eid`, `igshid` dropped from the query, the rest of the query kept **exactly as written**, empty path becomes `/`, one trailing slash dropped, invalid characters percent-encoded as Foundation does. The Swift and JavaScript implementations must agree byte for byte: both are checked against `Modules/Account/Tests/AccountTests/Resources/url-canonicalization.json`. Change both and the vectors together.
- **Columns.** `url` = canonical URL; `externalURL` = the address as saved, when it differs (extraction fetches it first); `title`; `contentHTML` = the extracted, sanitized body, **nil means the page hasn't been extracted yet**; `summary` = Readability's excerpt; `imageURL` = lead image; `authors` = byline. `datePublished` and `dateModified` are always nil, so every date sort and query uses `dateArrived`, the date saved ("Date Saved" in the UI). The page's own publication date and site name go in a small line at the top of the stored HTML (`ExtractedContentFormatter`).
- **Lists.** Inbox = unread (`UnreadFeed`, class name kept because state restoration stores it), Starred, Archive = read (`FetchType.read`), All = `.feed(readingListFeed)`. Archive is marking read; there is no separate archived flag.
- **Delete** is hard and removes both the article row and its status row (`ArticlesTable.delete` deletes statuses too), so a re-save starts fresh. `Account.delete(articleIDs:)` posts `.AccountDidDeleteArticles`; timelines remove those rows directly, because their fetch-and-merge keeps rows that vanish from a fetch.
- **Nothing is deleted automatically.** NetNewsWire's retention rules (feed-based cleanup, the 183-day read-on-insert rule, deleting articles that disappear from a feed, the weekly content cleanup) are gone; `RetentionTests` and `CloudKitContentSyncTests` guard that.

## iCloud

- Private database, container `iCloud.<ORGANIZATION_IDENTIFIER>.NetNewsList`. Zone `Account` holds the feed record; zone `Articles` holds, per article, an `ArticleStatus` record `s|<articleID>` (`webFeedExternalID`, `read`, `starred` as "0"/"1" strings) and an `Article` record `a|<articleID>` (`webFeedURL`, `uniqueID`, `url`, `externalURL`, `title`, LZFSE-compressed `contentHTMLData`/`contentTextData`, …) with a `DELETE_SELF` reference to the status record. A compressed body over 700 KB goes in a `contentHTMLAsset` CKAsset instead (1 MB record limit).
- **Sync status keys** (`SyncDatabase`): `.new` for an article's first upload (a lone `.new` uses save-if-new, so two devices saving the same page don't clobber each other), `.content` when its body changed after the first upload (uploads the whole record with `.changedKeys`), plus `.read`, `.starred`, `.deleted`. Without `.content`, a body extracted after the first upload would never reach iCloud. A content upload that fails is re-queued as `.content`.
- **The kick.** Saving, updating content and deleting call `storeAndSendArticleChanges`, which clears the no-change backoff and sends immediately; otherwise a save could wait 30 minutes.
- **Change tokens** live in `UserDefaults.standard` (`cloudkit.server.token.<zone>.<owner>`) and survive database wipes. Reset iCloud Sync (Mac app menu, iOS Settings > Troubleshooting) clears them and re-runs the first-launch sequence. If iCloud data is deleted, local data is kept and re-uploaded.
- **First launch:** find or create the account record, then save the feed record once per install, then fetch, then subscribe to both zones (once per install).
- **Unsigned builds** (tests, CI) trap when they create a `CKContainer`, so the container and zones are created lazily and never under unit tests.

## Saving and extraction

- **Ingress.** Every way in ends at `ExtractionCoordinator.saveArticle(url:title:body:)`: the Add Article sheet, `netnewslist://add` (Mac: `AppDelegate+URLHandling`, which returns focus to the browser; iOS: `SceneDelegate`), the `SaveArticleIntent` App Intent (runs in the app, may run in the background), dropped links (`DroppedWebPages`, Mac), and the share extensions. Extensions can't use iCloud or run extraction, so they write a `SavedArticleRequest` property list into `<app group>/Inbox/` (one file per request) and `SavedArticleRequestProcessor` saves them at launch, on new files, on foreground and in the iOS background refresh. The browser extension's remote mode writes the two iCloud records directly (see `chrome-extension/README.md`).
- **Extraction** (`Modules/Extraction`, driven by `Shared/Extraction/ExtractionCoordinator`): `PageFetcher` does one GET in a fresh ephemeral session (browser user agent, 20 s, 5 MB, HTML only, charset from the header, `<meta>` or UTF-8). **Don't use RSWeb's `Downloader` for this**: it caches error responses, so Retry would get the same failure. `ReadabilityWebExtractor` keeps one hidden `WKWebView` with page JavaScript off and runs Readability.js 0.6.0 and DOMPurify 3.4.16 in an isolated content world on a `DOMParser` document, which never runs the page's scripts or loads its resources. "Retry with Live Page" loads the real page with JavaScript on, waits 1.5 s and extracts the rendered DOM. A body under 100 characters counts as a failure.
- **Who extracts.** The device that saved the page, at once; and any device that sees a pending article (on launch, foreground and after each iCloud fetch). A local `ExtractionLedger` (JSON in the account folder, never synced) records failures and allows three automatic attempts (immediately, after 1 minute, after 10 minutes), then waits for Retry. Extraction runs only in the foreground: on iOS it pauses when the app goes to the background.
- **Stored content never runs scripts.** The article view sets `allowsContentJavaScript = false` for stored bodies; the "Allow JavaScript in original pages" preference (Mac) applies only to Show Original, which shows the live page in a separate plain web view without the article scripts. On iOS, Show Original opens the in-app browser.

## Offline images

The stored HTML keeps the original image URLs. When an article is shown, `ArticleImageRewriter` points each `<img>` at `nnlasset://<articleID>/<base64url(original URL)>` and drops `srcset`; `ArticleAssetSchemeHandler` serves the copy from `ArticleAssetStore` (`Application Support/NetNewsList/ArticleAssets/<articleID>/<sha256(url)>`, not backed up, not synced), downloading it if missing and showing a placeholder if that fails. `ArticleAssetCoordinator` downloads an article's images when it gets a body (40 images, 25 MB per article, 1600 px), deletes them with the article, and tidies orphans at launch. Don't put them in `Caches`: `CacheCleaner` empties `Caches/Images` every three days.

## Traps

- `articles natural join statuses` is how every query reads articles: never add a column with the same name to both tables.
- `SidebarItemIdentifier` values are persisted in window state; unknown ones are ignored, not asserted.
- `main.js`'s `convertImgSrc` leaves `scheme://` sources alone; that is what lets `nnlasset://` work.
- The Xcode project uses file-system-synchronized groups: a new file under `Mac/`, `iOS/` or `Shared/` is in the app targets automatically; extension targets compile only the files listed in their exception sets in `project.pbxproj`. Build settings belong in `xcconfig/`; a build phase fails the Mac build if the project file gains any.
- The Mac app group is Team-ID-prefixed (`<team>.<org>.NetNewsList`), the iOS one is `group.<org>.NetNewsList.iOS`; the `AppGroup` Info.plist key must match the entitlements or extensions can't reach the inbox.
- The browser extension's CloudKit API token is per environment (Development for Xcode builds, Production after the schema is deployed) and isn't committed (the repository is public); it goes in the extension's options or a git-ignored `chrome-extension/local-config.json`. Each web auth token is good for one request; the replacement comes back in the `X-Apple-CloudKit-Web-Auth-Token` response header. Advanced Data Protection must stay off for web sign-in to work.
