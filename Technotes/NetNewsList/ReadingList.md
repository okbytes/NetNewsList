# How NetNewsList works

NetNewsList is NetNewsWire with feeds replaced by saved pages. This note describes the pieces that are new or that behave differently from NetNewsWire, and the traps that cost time. `Plan.md` has the history: the decisions (D1–D7), the traps found before the work (section 4) and a progress note per PR.

## Data model

- **One account, one feed.** There is exactly one account, iCloud (`AccountManager.shared.defaultAccount`, `AccountType.cloudKit`, folder `Accounts/2_iCloud`). Every saved article belongs to one synthetic feed whose URL and feed ID are `netnewslist://reading-list` (`Account.readingListFeedURL`), created by `ensureReadingListFeed()` and never shown. Its iCloud record name is `md5(url)`, so every device creates the same feed. Never change that URL: it is part of every article ID.
- **Article identity.** `uniqueID` is the canonical URL (`URLCanonicalizer`); `articleID = md5("netnewslist://reading-list <canonical URL>")`. The same page saved on two devices is one article. Canonical form: lowercase scheme and host, default port dropped, fragment dropped, `utm_*`, `fbclid`, `gclid`, `dclid`, `msclkid`, `mc_cid`, `mc_eid`, `igshid` dropped from the query, the rest of the query kept **exactly as written**, empty path becomes `/`, one trailing slash dropped, invalid characters percent-encoded as Foundation does. It's checked against `Modules/Account/Tests/AccountTests/Resources/url-canonicalization.json`; change the rules and the vectors together, since a one-character difference between devices' builds makes the same page a second article.
- **Columns.** `url` = canonical URL; `externalURL` = the address as saved, when it differs (extraction fetches it first); `title`; `contentHTML` = the extracted, sanitized body, **nil means the page hasn't been extracted yet**; `summary` = Readability's excerpt; `imageURL` = lead image; `authors` = byline. `datePublished` is the date saved ("Date Saved" in the UI), not the page's own date: the time of the save in the apps (for a share, when it was shared: `SavedArticleRequest.dateRequested`), or, for the 97 pages imported once from Matter (2026-10-11, Plan.md), an estimate of when they were saved there. Unlike `dateArrived`, which each device sets when an article reaches it, it syncs, so every device shows the same date and order; sorts use `coalesce(datePublished, dateModified, dateArrived)`. Nothing removes it: `updateArticleContent` keeps it, a record without one leaves the stored one (`ArticlesTable.update`, in memory as on disk), and an upload leaves a missing date out instead of erasing iCloud's (`makeArticleRecord`). Pages saved before 2026-10-12 had none; see "Saved dates" below. `dateModified` is nil. The page's own publication date and site name go in a small line at the top of the stored HTML (`ExtractedContentFormatter`).
- **Lists.** Two: Queue = unread (`UnreadFeed`, class name kept because state restoration stores it) and Archive = read (`FetchType.read`); `SmartFeedsController.list(for:)` says which one an article is in. Archiving is marking read, and only an explicit Archive does it: opening an article doesn't. The UI shows no read state otherwise (no unread dots, Next Unread, read filter, Clean Up or Archive Above/Below) and no starring; the `starred` status still exists in the database and iCloud, unused. When a status changes, both timelines drop rows that left the list and fetch in ones that joined (`keepOnlyListMembers(changed:)` in the Mac `TimelineViewController` and iOS `SceneCoordinator`); archiving the open article (or moving it back to the Queue) closes it: on the Mac nothing is left selected and the list takes focus; on the iPhone the article pops back to the list first and its row then leaves (`SceneCoordinator.closeArticle`), as Mail does with "return to list". The Queue count is the "N in Queue" subtitle; there's no app badge, and neither app asks for notification permission (2026-10-22). Both lists sort oldest first by default; the sort setting (iOS Settings, Mac View › Sort Articles By) flips both.
- **Delete** is hard and removes both the article row and its status row (`ArticlesTable.delete` deletes statuses too), so a re-save starts fresh. `Account.delete(articleIDs:)` posts `.AccountDidDeleteArticles`; timelines remove those rows directly, because their fetch-and-merge keeps rows that vanish from a fetch. An archive (or star) queued here for an article that iCloud deleted first isn't sent (`CloudKitArticleStatusUpdate` needs the article for anything but a delete): it would put back a status record, read, that every device keeps. A new save whose status arrived without it (archived elsewhere before a delete was seen) is marked unread, so saving always puts the page in the Queue.
- **Nothing is deleted automatically.** NetNewsWire's retention rules (feed-based cleanup, the 183-day read-on-insert rule, deleting articles that disappear from a feed, the weekly content cleanup) are gone; `RetentionTests` and `CloudKitContentSyncTests` guard that.

## iCloud

- Private database, container `iCloud.<ORGANIZATION_IDENTIFIER>.NetNewsList`. Zone `Articles` holds, per article, an `ArticleStatus` record `s|<articleID>` (`webFeedExternalID`, `read`, `starred` as "0"/"1" strings) and an `Article` record `a|<articleID>` (`webFeedURL`, `uniqueID`, `url`, `externalURL`, `title`, LZFSE-compressed `contentHTMLData`/`contentTextData`, …) with a `DELETE_SELF` reference to the status record. A compressed body over 700 KB goes in a `contentHTMLAsset` CKAsset instead (1 MB record limit). The feed exists only on each device (`ensureReadingListFeed`, external ID `md5(url)`, which status records carry as `webFeedExternalID`); incoming articles find it by `webFeedURL`. Builds before 2026-10-22 also kept a feed record and an account record in a zone `Account`; nothing reads or writes it now, and deleting it in CloudKit Console loses nothing.
- **Sync status keys** (`SyncDatabase`): `.new` for an article's first upload (it uses save-if-new, so two devices saving the same page don't clobber each other, also when an archive, a star or a body was queued with it before it went: a status change then goes as a status update too, and the article as a first upload), `.content` when its body changed after the first upload (uploads the whole record with `.changedKeys`), plus `.read`, `.starred`, `.deleted`. A deletion from iCloud doesn't remove an article whose `.new` from a save made here is still pending (the row's flag is set; Reset iCloud Sync queues its re-uploads with the flag off). An article deleted here and then saved again before the delete went has `.deleted` and `.new` queued and exists again: it goes up whole (`.all`) instead of the delete. Without `.content`, a body extracted after the first upload would never reach iCloud. A content upload that fails is re-queued as `.content`.
- **A page saved in two places at once.** A pending, content-less record pair (another device's URL-only save) can already be in iCloud when this device saves the same page. Its first upload, save-if-new, then finds the records there (`serverRecordChanged`, now returned by `CloudKitZone.saveIfNew`). iCloud's copy is always merged into the article here (`CloudKitArticlesZoneDelegate.mergeICloudCopies`, articles still stored here only, so one deleted meanwhile isn't brought back): its title, address and saved date replace the local ones, and a local body, excerpt, image and byline are kept when the copy has none. If the copy has no body and this device has one, the body goes up as `.content` in the same send run; a copy that already has a body stays (the first body in iCloud wins, so Reset iCloud Sync can't overwrite newer bodies everywhere, and an anonymous extraction that gets there first beats a later Safari or Shortcut capture). First uploads iCloud refuses for another reason (storage full) are queued again after the run. On receipt, a record without a body doesn't replace a local body while this device has a pending `.new` or `.content` for it (`ArticlesTable.update`'s `keepingContentOf`, in the write's transaction); with nothing pending, the record wins, so a page deleted and saved again elsewhere starts fresh.
- **Saved dates.** Pages saved in the apps before 2026-10-12 had no `datePublished`, so each device showed when it received them (a new device: its install time for all of them). After the first successful fetch of each launch (`refreshArticleStatus`, which the Mac's timer sync and every full refresh go through), a device offers the time each page arrived here for a page with no saved date or one whose saved date is more than a minute later (`Account.savedDateProposals`, one SQL query). It reads those Article records' `datePublished` from iCloud, keeps iCloud's date when it's at most a minute later, and otherwise writes its own with save-if-unchanged, so a date another device wrote meanwhile isn't overwritten (`CloudKitArticlesZone.SavedDatePlan`, `CloudKitAccountDelegate.settleSavedDatesIfNeeded`); an article iCloud has no record of keeps the offered date here. Every device thus converges on the earliest time any device had a page; a page saved since carries its save time, which is never later than its arrival anywhere, so it's never offered. Known: a page deleted and saved again before another device saw the delete can get its first date back from that device.
- **The kick.** Saving, updating content and deleting call `storeAndSendArticleChanges`, which clears the no-change backoff and sends immediately; otherwise a save could wait 30 minutes.
- **Change tokens** live in `UserDefaults.standard` (`cloudkit.server.token.<zone>.<owner>`) and survive database wipes. Reset iCloud Sync (Mac app menu, iOS Settings > Troubleshooting) clears them and re-runs the first-launch sequence. If iCloud data is deleted, local data is kept and re-uploaded.
- **First launch:** create the Articles zone (saving one that exists changes nothing) and mark the account set up (`account.externalID`, `CloudKitAccountDelegate.accountExternalID`; older installs have their old account record's name there), then fetch, then subscribe to the zone (once per install). When the Articles fetch reports that the user deleted the app's iCloud data (`userDeletedZone`), the zone is created again at once, fetched from the start with a fresh change token (`CloudKitArticlesZone.recreateDeletedZone`, from a fetch or a send), and everything on the device is kept; Reset iCloud Sync uploads it. The account delegate then subscribes the new zone to change pushes, which went with the old one; if that fails it tries again at the next launch.
- **Unsigned builds** (tests) trap when they create a `CKContainer`, so the container and zones are created lazily and never under unit tests.

## iCloud on the web

The CloudKit framework only ever uses the iCloud account macOS is signed in to, and a managed work Mac can't be signed in to the user's. So the Mac app has a second way to reach the same private database: CloudKit Web Services (REST), with an Apple ID sign-in that belongs to the app alone. Nothing here has run against real iCloud yet: it was built from Apple's documentation, CloudKit JS and other clients' reports, and tested against a fake server that encodes them (`build/WebSyncTestSuite/`, not committed; see Plan.md, 2026-10-13).

- **Which way.** `CloudKitWebSync.isEnabled`: Info.plist `NetNewsListICloudTransport` = `web` (the work build, `scripts/build-work-mac.sh`), or a `-NetNewsListICloudTransport web` launch argument on any build (sign in with the same Apple Account the Mac's own iCloud uses: the different-account check below only knows earlier web sign-ins). Everything else is unchanged: the zones, their delegates, the sync database and the UI run the same code. `CloudKitAccountDelegate` gives the zones a `CloudKitWebDatabase` instead of a CKContainer (never created in this mode; the work build has no iCloud entitlement, so creating one would crash), and each `CloudKitZone` operation hands over to its counterpart in `CloudKitZone+Web.swift`. iOS never uses it.
- **Sign-in.** NetNewsList menu › Sign In to iCloud… (shown only in this mode, and opened at launch while signed out) loads Apple's sign-in page, fetched fresh each time the window opens, in a web view with its own persistent website data store (`ICloudSignInWindowController`). The page ends by sending the browser to the API token's sign-in callback with the token in `ckWebAuthToken` (and again in `ckSession`); the window cancels that navigation, so the token never reaches the callback host. `CloudKitWebService.verifySignIn` spends it at once on `users/current` (tried twice on a network hiccup) without storing anything; `CloudKitWebSync.completeSignIn` then compares the account with the last web sign-in's (`CloudKitWebUserRecordName`) and, for a different Apple Account, asks before `adopt` stores it. A failed sign-in doesn't navigate: Apple's page posts to `window.opener`, so a script stands in for one and forwards the message (`accessError` means web access to iCloud data is off, as Advanced Data Protection forces). The API token and environment come from Info.plist `CloudKitAPIToken`/`CloudKitEnvironment`, which the work build fills from the git-ignored `local-config.json` at the repository's root; a build without one (a release from `scripts/release-work-mac.sh`, which can't carry it: the repository is public) asks for it at sign-in, or at launch when a sign-in is already stored, keeps it in user defaults across updates, and asks again if iCloud refuses it.
- **The token** is good for one request (`X-Apple-CloudKit-Web-Auth-Token` on each response carries the next), so `CloudKitWebService` (an actor) sends one request at a time and stores each replacement in the login keychain (`KeychainWebAuthTokenStore`, with a copy in memory), but only while the stored token is still the one the request used, so a sign-out or new sign-in during a request stays. The token it replaced is kept too (`previousWebAuthToken`): when a response is lost (the Mac slept or the app quit while a request was out), the stored token is already spent and the one before it is all that might still be good. `CloudKitWebSync.isSignedIn` reads the store, which the service updates before it posts `CloudKitWebSignInDidChange`. Apple's rule: a token expires 30 minutes after it is created, or 2 weeks when the sign-in was made with Keep me signed in (the sign-in page ticks it, `ICloudSignInPage.keepMeSignedInScript`; a page that renders the box differently defeats the script, so check it when Apple changes the page), and each replacement is a new token. iCloud ends a sign-in with AUTHENTICATION_REQUIRED/FAILED, or ACCESS_DENIED for the private database (web access turned off, or Advanced Data Protection on: `webAccessDisabled`). A refusal of the token isn't final at once: the request goes again with the token the refusal's answer carried if it had one, else with the same token after 5 seconds (Apple has refused good tokens for a moment); a second refusal tries the previous token, last because storing it drops the current one; only a third ends the sign-in (`perform(refusals:)`). The post then carries `endedByICloud`, and the Mac app tries to sign in again by itself before it tells the user (below). A bare 421 is HTTP/2's Misdirected Request and is retried. While signed out nothing is sent; signing in syncs at once, and runs the first-launch setup if it never ran.
- **Renewal without the user.** Apple's sign-in page keeps its own website data between sign-ins (the `ICloudSignInPage` store), so when Apple still recognizes this Mac the page goes straight to the callback with a fresh token. `ICloudSignInRenewer` loads it in a web view that isn't shown and takes that token (25 s limit, at most once an hour unless iCloud just ended the sign-in): when iCloud ends the sign-in, at launch when a sign-in is missing but this Mac signed in before (`CloudKitWebSync.hasSignedInBefore`), and when the current sign-in is older than 10 days (`CloudKitWebSync.signInDate`, checked hourly and after wake), so a two-week sign-in is replaced before it runs out. When the page wants the user (a password, a code, an error, or it just doesn't finish), the app shows the sign-in window, and bounces the Dock icon once when it's in the background (it posts no notifications); a sign-in for a different Apple Account opens the window with the question. Whether Apple's page completes by itself, and for how long after a sign-in, hasn't been seen on the work Mac yet (TODO-Brett.md). Over the web `applicationShouldTerminate` sends what's pending and waits for the request that's out (8 s, then 4 s more for the answer) before the app quits, since a quit mid-request (an update, a restart) would leave a spent token. The send waits on a sync operation that ignores cancellation, so it runs in a task of its own that the quit stops waiting for after 8 s; from then on no new request starts, a retry after a refused token included (`CloudKitWebService.stopSending`), and a quit never takes more than about 12 s.
- **No pushes.** There are no subscriptions over the web, so the 30-minute quiet-period backoff is off and `ArticleStatusSyncTimer` keeps its 2-minute cadence: one `changes/zone` request every two minutes when nothing changed.
- **Mapping.** `CloudKitWebDatabase` turns requests and answers into CKRecords and CKErrors (`CloudKitWebRecordCoder`), so retries, zone creation and conflict handling work as before. A `.changedKeys` save is `forceUpdate` with the record's `changedKeys()` (fields left out stay as they are in iCloud, which is what keeps a saved date safe); save-if-new is `create`, or `update` with the change tag for a record fetched earlier (`CloudKitWebChangeTags` remembers tags per CKRecord object, since a CKRecord made here can't carry one); deletes are `forceDelete`. A save that finds iCloud's copy (`EXISTS`/`CONFLICT`) gets that copy as its `serverRecord` through small, retried lookups; when the copy can't be fetched, the save is reported as failed, not as a conflict, so it goes again later instead of uploading over the copy. Responses don't echo fields (`desiredKeys: []`). Requests carry at most 200 operations and about 2 MB, and a request iCloud refuses as too big (or as invalid) is halved until each record gets its own answer. An atomic request refused without a culprit, or failed only by deleting a record already gone, goes again without it or record by record; a record iCloud's answer doesn't mention counts as not saved.
- **Things the REST API does differently.** Deletions in `changes/zone` come without a record type: the Articles zone infers it from the name (`s|`, `a|`). A fetch without a sync token lists the zone's whole history, deletions from long ago included; an article whose first upload is still pending here survives a deletion (both ways in, `CloudKitArticlesZoneDelegate.delete`), so saving a page again before the first sync isn't undone. There's no expired-token error: a sync token iCloud no longer takes comes back as `BAD_REQUEST`, which refetches the zone from the start once. There's no "user deleted the zone": a missing zone is recreated. Clearing a field (`{"value": null}`) isn't documented: if iCloud refuses it, the save goes again without clearing, leaving a stale value rather than saving nothing. If iCloud instead ignores it silently, the one visible effect is rare: a body replaced by one too big to stay inline (Retry with Live Page on a very long page) keeps the old inline copy, which readers prefer to the asset. Assets upload to the address `assets/upload` returns and download from the record's `downloadURL` on a separate URL session; a download refused for good is tried once more through a lookup (a fresh address), then that record is skipped until it next changes, never handed on without its body. iCloud can ask to wait for hours, in a refused answer or inside one that worked (one record's or zone's wait is held 15 minutes at most); past a minute, sync requests fail at once until then and the next timer run tries again. The sign-in page and its check aren't held off, and signing out or in clears the wait.
- **Change tokens** are CloudKit Web Services sync tokens, kept under `cloudkit.web.token.<zone>.<owner>`, apart from the framework's, so a copy switched between the two never hands one a token from the other. Reset iCloud Sync clears both.
- **Limits.** Advanced Data Protection must stay off (no web token can be issued with it on, and a token issued before turns into `ACCESS_DENIED`). In August–October 2026 some developers reported web sign-in tokens refused with 421 for reasons on Apple's side; nothing in the app can work around that.

## Saving and extraction

- **Ingress.** Every way in ends at `ExtractionCoordinator.saveArticle(url:title:body:)`: the Add Article sheet, `netnewslist://add` (`netnewslist-dev://add` for the Mac Debug build, NetNewsList Dev, so links reach the installed app; Mac: `AppDelegate+URLHandling`, which returns focus to the browser; iOS: `SceneDelegate`), the `SaveArticleIntent` App Intent (runs in the app, may run in the background), dropped links (`DroppedWebPages`, Mac), the Services menu item "Save to NetNewsList" (Mac, `SavePageService`, `NSServices` in Info.plist: a selected link or address, or every web address in selected text; it shows only when the selection contains one; text with spaces in it is never taken as one address, and text holding several, like lines of links, saves each, dragged or through Services, while a dragged article or a link a browser names saves its link alone), and the share extensions. Extensions can't use iCloud or run extraction, so they write a `SavedArticleRequest` property list into `<app group>/Inbox/` (one file per request) and `SavedArticleRequestProcessor` saves them at launch, on new files, on foreground and in the iOS background refresh.
- **Extraction** (`Modules/Extraction`, driven by `Shared/Extraction/ExtractionCoordinator`): `PageFetcher` does one GET in a fresh ephemeral session (browser user agent, 20 s, 5 MB, HTML only, charset from the header, `<meta>` or UTF-8). **Don't use RSWeb's `Downloader` for this**: it caches error responses, so Retry would get the same failure. `ReadabilityWebExtractor` keeps one hidden `WKWebView` with page JavaScript off and runs Readability.js 0.6.0 and DOMPurify 3.4.16 in an isolated content world on a `DOMParser` document, which never runs the page's scripts or loads its resources. "Retry with Live Page" loads the real page with JavaScript on, waits 1.5 s and extracts the rendered DOM; a page that moves on with a script or a meta refresh (a link shortener's) and is still loading then gets up to 5 s more to load where it goes, and 1.5 s to render (`liveRedirectLimit`); a first load the redirect cut short (cancelled or interrupted) counts as moved on, not failed, and a destination that fails to load fails the live load (`liveNavigationError`) rather than leaving the page that sent the browser on to be read. A fetched page that comes back with under 100 characters of text (often one its own scripts build) gets one live load automatically (`ExtractionCoordinator.extractStaticOrLive`), which runs the site's scripts, ads and trackers in a store that's thrown away; when that fails or reads no better, the failure is "No article text was found". Before Readability, `prepare.js` (also built into Safari's capture, `SafariExt.js`) removes Tailwind's layout classes (`overflow-*`, `scroll-*`), which match Readability's "hidden"/"scroll" class penalty and made it drop code blocks and figures; rebuilds react-tweet embeds (`.react-tweet-theme`) as quotes in X's embed form (text, photos at `name=large`, "— Name (@handle) date" with the date the only link, so Readability's link-density check keeps them); and joins code lines a highlighter put in `<div>`s with line breaks (Readability deletes empty `<div>`s, losing blank lines, and wraps each line in a `<p>`; an empty line that already holds a line break gets no second one). The static extraction also puts back what React streamed: a Next.js page sends the parts that weren't ready (often code samples) at the end of the HTML in hidden `<div id="S:n">`s with `$RC`/`$RR`/`$RS` calls that move them into place. The calls are read from the raw HTML, since DOMParser leaves `<script>`s out with scripts off, and only parts holding code, images, video, a table or a paragraph of 80+ characters, and no form fields or tree, grid, listbox, slider, spinbutton or toolbar role, are moved; interactive demos stay out (their labels and counters read as noise). A live page or a Safari capture already has them in place, demos included. A body under 100 characters counts as a failure. When extraction finishes, the title loses the site's name after it (` / claude.dev Blog`, or after `|`, `-`, `–`, `—`, `·`, `:` or `»`) when the page names its site (`ExtractedContentFormatter.storedTitle`), including a title the save brought with it, like Safari's.
- **Who extracts.** The device that saved the page, at once; and any device that sees a pending article (on launch, foreground and after each iCloud fetch). A local `ExtractionLedger` (JSON in the account folder, never synced) records failures and allows three automatic attempts (immediately, after 1 minute, after 10 minutes), then waits for Retry. A failure because the device is offline (not connected, cellular data off for the app, roaming off), also when the automatic live load meets it, isn't counted: the page stays pending for the next launch, foreground or iCloud download. Extraction runs only in the foreground: on iOS it pauses when the app goes to the background, and a launch into the background (a background refresh, a silent push, a Shortcut) leaves pages pending until the app first becomes active, so a cut-short job never counts against a page. A failed extraction keeps the page's title only for an article that has neither title nor body: `updateArticleContent` never replaces a body with nothing.
- **Stored content never runs scripts.** The article view sets `allowsContentJavaScript = false` for stored bodies. Neither app shows a live page itself: Open in Browser and links tapped in an article go to the system browser. The only web pages the apps load are the hidden extractor's (Retry with Live Page and the automatic live load, X posts) and, in a copy that syncs over the web, Apple's iCloud sign-in page.

## X posts

- **Links.** `URLCanonicalizer` turns a link to an X post on any X host (`x.com`, `twitter.com`, their `www.`/`mobile.` forms, the `fxtwitter`/`vxtwitter`/`fixupx`/`fixvx` mirrors), with any screen name, `/photo/N` suffix or `?s=…&t=…` share parameters, into `https://x.com/i/status/<id>`. `URLCanonicalizer.xPage(for:)` says whether a link is an X post or an X Article (`/<user>/article/<id>`, `/i/article/<id>`).
- **Extraction.** X's static page is a sign-in wall for everyone, and Readability used to save it as the post. X pages are always read live and signed out, as anyone on the web sees them: `ReadabilityWebExtractor.extractXPage` loads the post at `https://x.com/i/status/<id>` (no redirects) in a non-persistent store, with X's scripts on and a 30 s limit, as desktop Safari on both platforms (`xUserAgent`: X sends an iPhone web view to its app's URL scheme, and Mobile Safari to a phone layout `x.js` doesn't read), waits for `netNewsListX.state` (`x.js`) to report the post, then `netNewsListX.extract` rebuilds it as plain HTML: the post and the author's posts directly before and after it (a thread), text with links and line breaks, photos at `name=large`, video posters linked to the post, quoted posts as blockquotes; for an Article (`.x-article-body` inside the post), the cover, title and body blocks with embedded posts as quotes. A post can be one word or just a photo, so X pages skip the 100-character minimum. A body supplied by a share (Safari's Readability capture) is ignored for X links.
- **X's page.** Signed out, X serves a server-rendered client with utility class names and no `data-testid`s: `<article>` per post, the status link `/<handle>/status/<id>` next to an inline script that carries the timestamp, a `dir="auto"` text block, `pbs.twimg.com/media` images and `.x-article-body`; a copy of the shared post comes first and the conversation follows (hidden), so each post's last occurrence wins. A quoted post is a nested `<article>` inside a `[role="link"]` frame whose own hidden link points to the quoted post, so a post's own elements are the ones outside its quote frames (`own`); before 2026-10-22 that hidden link made the quoted post's ID the shared post's, and a quote post whose conversation didn't repeat it timed out. The copy at the top has no timestamp script, so a post without one is dated from its ID (since late 2010 an ID is the milliseconds since X's epoch, 1288834974657, shifted left 22 bits). A cut-off quoted post ends in a "Show more" button, which is left out of the text and becomes "Read the rest on X". A video's poster also appears as an image of the post; it's kept once, as the video's, at `name=large`. X can still add to the page after the post renders, so the extractor polls `netNewsListX.signature()` until it stops changing (a second, at most 6 s), in a 4000-point-tall web view, and starts polling as soon as the page loads rather than after every image. When X changes its page, check it with `Tools/extract-page`, which runs exactly the app's X path.
- **No X account.** The app used to sign in to X (`XAccount`, a website data store of its own, a keychain copy of its cookies, a sign-in window on the Mac and a Settings row on the iPhone), and signed in X served its classic client, which `x.js` also read. The user closed their X account, and both were removed on 2026-10-22 (`git log -S XAccount` finds them). At launch `ExtractionCoordinator.removeXSignInLeftovers` removes what the sign-in left on a device, its website data store and the keychain item; delete it once every device has run it. A page that shows only X's sign-in wall (a protected account, a post X hides from signed-out people, or X turning off signed-out viewing) fails with `ExtractionError.signInRequired`.

## Offline images

The stored HTML keeps the original image URLs. When an article is shown, `ArticleImageRewriter` points each `<img>` at `nnlasset://<articleID>/<base64url(original URL)>` and drops `srcset`; `ArticleAssetSchemeHandler` serves the copy from `ArticleAssetStore` (`Application Support/NetNewsList/ArticleAssets/<articleID>/<sha256(url)>`, not backed up, not synced), downloading it if missing and showing a placeholder if that fails. `ArticleAssetCoordinator` downloads an article's images when it gets a body (40 images, 25 MB per article, 1600 px), deletes them with the article, and tidies orphans at launch and then daily. After an article has been in the Archive for 30 days, each device drops its images (iCloud keeps the text; opening the article downloads them again, if the site still has them, and the next daily pass drops them again). The clock is local: the store notes when this device first saw an article in the Archive (`StatusesDidChange` for `read`, here or from another device, and each pass) in `ArticleAssets/.archive-dates.json` (the leading dot keeps it out of `storedArticleIDs()`), forgets it when the article returns to the Queue (which downloads its images again) or is deleted, and prefetching skips articles past the 30 days. Only articles still in the Archive lose images, whatever the file says. Don't put them in `Caches`: `CacheCleaner` empties `Caches/Images` every three days.

## Backups

iCloud sync isn't a backup: the Mac, the iPhone and iCloud mirror each other, so a mistaken delete, a sync bug or a Retry that replaces good text with a paywall teaser reaches every copy within a minute. This Mac has no Time Machine, and the iCloud data lives in CloudKit's Development environment. So the Mac app keeps its own snapshots: `ReadingListBackups` (Mac only) writes `Application Support/NetNewsList/Backups/NetNewsList <yyyy-MM-dd HH.mm.ss>.json` in the app's container at launch and then once a day (checked hourly against the clock, so sleep counts), skips the write when the newest snapshot has the same bytes, and keeps the newest 30. File > Show Backups in Finder reveals them. The JSON (`Account.readingListBackupData()`, `formatVersion` 1) lists every article, Queue and Archive, oldest first: `articleID`, `url` (canonical), `externalURL`, `title`, `contentHTML` (null = not extracted yet), `summary`, `imageURL`, `authors`, `dateSaved` (`datePublished ?? dateModified ?? dateArrived`, ISO 8601) and `isArchived`. Images aren't included; they're downloaded again from their original addresses. There is no Restore command: if one is ever needed, it's a one-off like the Matter import (Plan.md, 2026-10-11): put back the articles that are missing, with `dateSaved` as `datePublished` and `isArchived` as read, and upload them.

## Interface

Pared down on 2026-10-11 (Plan.md has the details). Both apps open on the Queue at every launch; the Archive is secondary. On iOS the Queue is the root screen: its name in heavy type on the left of the bar, with the Queue's count in a small chip in the title's color, centered on the title's lowercase letters (the text knocked out of it, after Verbatim's library title and badges), and "…" on the right (a menu: Add Article first, then Archive and Settings); Archive pushes onto the same stack, its name beside a chevron-only back button and no chip; Settings is a sheet with a grabber and no Done button; tapping a row pushes the article, whose top bar has Archive / Move to Queue, Open in Browser and Share (Find in Article and Open in Browser are in the share sheet). The iPad shows the list and the article side by side. The Mac window has two panes, the list and the article, under a compact toolbar; over the list the toolbar has the list's name in bold with a smaller count chip, also in the title's color (the window's own title is hidden but still set, for the Window menu), which switches between the Queue and the Archive when clicked (also Go › Queue ⌘1 and Go › Archive ⌘2), and "+" at the list's right edge; Archive / Move to Queue and Open in Browser are over the article. Gone from both: the sidebar, search, Archive All, in-app browsing (Show Original), article themes (only the built-in Default), full-screen articles, Group by Site and the timeline layout setting (rows on both are one line of title with a small icon, and the site and date below), the appearance setting (both follow the system), Help/About on iOS and the Mac Preferences window. iOS Settings keeps Sort Oldest to Newest and Troubleshooting. Archive and Move to Queue use `archivebox` and `tray.and.arrow.up` everywhere.

The article's body is set in Breve (DSType; the user's licensed fonts): Breve Text on the Mac, Breve News (DSType's cut for narrow columns) on the iPhone. The title and the body's headings (`h1`–`h6`) are in the system font, SF, in bold; WebKit sets SF's optical size from the font size, so large headings get its Display design without naming it (naming "SF Pro Display" only works where SF Pro is installed from Apple's developer site). The feed header, dateline and everything outside the article view keep the system font too. The installed files name every style as a family of its own, so `ArticleFonts` writes `@font-face` rules that gather them into the platform's body family (appended to the theme's CSS); the iOS block of stylesheet.css switches the body to Breve News. A Mac uses its installed copies (`local()` by PostScript name), so the work Mac shows Breve only if it's installed there. The iOS app carries whatever faces are in `iOS/Resources/ArticleFonts/` (git-ignored: licensed fonts must never reach the public repository; Breve News Book, Book Italic, Bold and Bold Italic, copied from `~/Library/Fonts`; on 2026-10-18 the News faces replaced the Breve Text ones, and the Breve Title Bold file left there is no longer used) and inlines the faces `ArticleFonts` defines in each page as `data:` URLs, about 1 MB a page. Without Breve, articles fall back to the system font. On the iPhone the article text is two steps above the Dynamic Type size (19px at the default 17, code 18px, the title 24px), and in dark mode the article screen is #151515 rather than black: the `articleBackgroundColor` asset for the views, the same value in stylesheet.css and the iOS blank.html for the page; change all three together.

Site icons (the list rows and the article header) come from `SiteFaviconCache`, by host. `FaviconDownloader` keeps the images in Caches/Favicons and the home page → icon URL map in `ImageMetadataDatabase` (the data folder). `CacheCleaner`'s 3-day purge leaves Favicons alone, so an icon downloads once (iOS can still clear Caches when storage runs very low; icons then download again), and after a launch `SiteFaviconCache` reads a stored icon from disk at once instead of waiting for the downloader's asynchronous read. The article header's icon (`nnwImageIcon` in template.html) hides itself when a site has none and shows again when one arrives.

## Traps

- `articles natural join statuses` is how every query reads articles: never add a column with the same name to both tables.
- `SidebarItemIdentifier` values still travel in Handoff activities (`sidebarItemID`) and may be in old saved state; unknown ones are ignored, not asserted. Neither app saves which list was showing: both open on the Queue.
- The keyboard-shortcut plists in `Shared/Resources/` are loaded by both apps; an entry removed for one app is gone from the other too.
- `main.js`'s `convertImgSrc` leaves `scheme://` sources alone; that is what lets `nnlasset://` work.
- A saved body keeps none of the site's styles (Readability drops classes, DOMPurify drops `style`), so `main.js` patches what usually breaks without them, on every display (pages saved earlier get it too): an SVG with ten or more shapes and no `fill`, `stroke` or `style` anywhere was coloured by the site's CSS and would paint solid black, so it's hidden; a heading's link to itself, judged by the link pointing at the article's own address (the page's base URL) or at the heading's id, is unwrapped when it holds the whole heading and removed when it's a mark (#, ¶, §, 🔗, a zero-width space or nothing) or the heading has words outside it (an icon with screen-reader words like "Copy link to heading"); a link with no text and no image, video or frame (`a[href]` only, so footnote targets stay) is removed; code lines in `<div>`s or `<p>`s inside a `<pre>` are joined with line breaks (pages saved before `prepare.js` did it); a heading typed in capitals gets `nnw-capitals` (small capitals in stylesheet.css); a caption's leading bold label and a code block's title bar or file name get the space the site's styles put between their words, and the title bar becomes a small label (`nnw-code-label`, in its own case). The title bar is the one element before the `<pre>`, taking in `<div>`s the `<pre>` fills alone, in a `<div>` of just the two, with 40 characters or fewer, no link or image, and no sentence punctuation at the end. stylesheet.css sets a link around whole blocks (a card pointing to another page) as a block with no underline, which otherwise showed as stray dots, and `pre code` without the inline code padding that pushed a code block's first line right. Charts a site marks `aria-hidden` are dropped by Readability, which leaves their screen-reader text.
- WebKit blocks fonts from a custom URL scheme (`nnlasset://` and the like) on an article page, because the page's base URL is the article's https address and that counts as mixed content; images from one are allowed. That's why the iOS app's Breve faces go in as `data:` URLs.
- The Xcode project uses file-system-synchronized groups: a new file under `Mac/`, `iOS/` or `Shared/` is in the app targets automatically; extension targets compile only the files listed in their exception sets in `project.pbxproj`. Build settings belong in `xcconfig/`; a build phase fails the Mac build if the project file gains any.
- The Mac app group is Team-ID-prefixed (`<team>.<org>.NetNewsList`), the iOS one is `group.<org>.NetNewsList.iOS`; the `AppGroup` Info.plist key must match the entitlements or extensions can't reach the inbox.
- xcodebuild registers every Mac app it builds with LaunchServices and unregisters it only on Clean Build Folder, so builds left in scratchpads stay registered, each with its own Save to NetNewsList (Dev) in the Services menu. Past three services a right-click menu moves them all into a Services submenu, which looks like the item disappeared. `scripts/unregister-stale-builds.sh` unregisters every copy but the installed app and Xcode's DerivedData. Chrome and Helium pass only a link's text to Services when you right-click a plain link, so the item never shows there.
- The CloudKit Web Services API token is per environment (Development for Xcode builds, Production after the schema is deployed) and isn't committed (the repository is public); the work build reads it from the git-ignored `local-config.json` at the repository's root. Advanced Data Protection must stay off for web sign-in to work.
