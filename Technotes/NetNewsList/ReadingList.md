# How NetNewsList works

NetNewsList is NetNewsWire with feeds replaced by saved pages. This note describes the pieces that are new or that behave differently from NetNewsWire, and the traps that cost time. `Plan.md` has the history: the decisions (D1–D7), the traps found before the work (section 4) and a progress note per PR.

## Data model

- **One account, one feed.** There is exactly one account, iCloud (`AccountManager.shared.defaultAccount`, `AccountType.cloudKit`, folder `Accounts/2_iCloud`). Every saved article belongs to one synthetic feed whose URL and feed ID are `netnewslist://reading-list` (`Account.readingListFeedURL`), created by `ensureReadingListFeed()` and never shown. Its iCloud record name is `md5(url)`, so every device creates the same feed. Never change that URL: it is part of every article ID.
- **Article identity.** `uniqueID` is the canonical URL (`URLCanonicalizer`); `articleID = md5("netnewslist://reading-list <canonical URL>")`. The same page saved on two devices, or from the browser extension, is one article. Canonical form: lowercase scheme and host, default port dropped, fragment dropped, `utm_*`, `fbclid`, `gclid`, `dclid`, `msclkid`, `mc_cid`, `mc_eid`, `igshid` dropped from the query, the rest of the query kept **exactly as written**, empty path becomes `/`, one trailing slash dropped, invalid characters percent-encoded as Foundation does. The Swift and JavaScript implementations must agree byte for byte: both are checked against `Modules/Account/Tests/AccountTests/Resources/url-canonicalization.json`. Change both and the vectors together.
- **Columns.** `url` = canonical URL; `externalURL` = the address as saved, when it differs (extraction fetches it first); `title`; `contentHTML` = the extracted, sanitized body, **nil means the page hasn't been extracted yet**; `summary` = Readability's excerpt; `imageURL` = lead image; `authors` = byline. `datePublished` is the date saved ("Date Saved" in the UI), not the page's own date: the time of the save in the apps (for a share, when it was shared: `SavedArticleRequest.dateRequested`), the click time from the browser extension's remote mode, or, for the 97 pages imported once from Matter (2026-10-11, Plan.md), an estimate of when they were saved there. Unlike `dateArrived`, which each device sets when an article reaches it, it syncs, so every device shows the same date and order; sorts use `coalesce(datePublished, dateModified, dateArrived)`. Nothing removes it: `updateArticleContent` keeps it, a record without one leaves the stored one (`ArticlesTable.update`, in memory as on disk), and an upload leaves a missing date out instead of erasing iCloud's (`makeArticleRecord`). Pages saved before 2026-10-12 had none; see "Saved dates" below. `dateModified` is nil. The page's own publication date and site name go in a small line at the top of the stored HTML (`ExtractedContentFormatter`).
- **Lists.** Two: Queue = unread (`UnreadFeed`, class name kept because state restoration stores it) and Archive = read (`FetchType.read`); `SmartFeedsController.list(for:)` says which one an article is in. Archiving is marking read, and only an explicit Archive does it: opening an article doesn't. The UI shows no read state otherwise (no unread dots, Next Unread, read filter, Clean Up or Archive Above/Below) and no starring; the `starred` status still exists in the database and iCloud, unused. When a status changes, both timelines drop rows that left the list and fetch in ones that joined (`keepOnlyListMembers(changed:)` in the Mac `TimelineViewController` and iOS `SceneCoordinator`); on the Mac the row that takes a removed selection's place is selected, as in Mail. The Queue count is the app badge and the "N in Queue" subtitle. Both lists sort oldest first by default; the sort setting (iOS Settings, Mac View › Sort Articles By) flips both.
- **Delete** is hard and removes both the article row and its status row (`ArticlesTable.delete` deletes statuses too), so a re-save starts fresh. `Account.delete(articleIDs:)` posts `.AccountDidDeleteArticles`; timelines remove those rows directly, because their fetch-and-merge keeps rows that vanish from a fetch.
- **Nothing is deleted automatically.** NetNewsWire's retention rules (feed-based cleanup, the 183-day read-on-insert rule, deleting articles that disappear from a feed, the weekly content cleanup) are gone; `RetentionTests` and `CloudKitContentSyncTests` guard that.

## iCloud

- Private database, container `iCloud.<ORGANIZATION_IDENTIFIER>.NetNewsList`. Zone `Account` holds the feed record; zone `Articles` holds, per article, an `ArticleStatus` record `s|<articleID>` (`webFeedExternalID`, `read`, `starred` as "0"/"1" strings) and an `Article` record `a|<articleID>` (`webFeedURL`, `uniqueID`, `url`, `externalURL`, `title`, LZFSE-compressed `contentHTMLData`/`contentTextData`, …) with a `DELETE_SELF` reference to the status record. A compressed body over 700 KB goes in a `contentHTMLAsset` CKAsset instead (1 MB record limit).
- **Sync status keys** (`SyncDatabase`): `.new` for an article's first upload (it uses save-if-new, so two devices saving the same page don't clobber each other, also when an archive, a star or a body was queued with it before it went: a status change then goes as a status update too, and the article as a first upload), `.content` when its body changed after the first upload (uploads the whole record with `.changedKeys`), plus `.read`, `.starred`, `.deleted`. A deletion from iCloud doesn't remove an article whose `.new` is still pending. Without `.content`, a body extracted after the first upload would never reach iCloud. A content upload that fails is re-queued as `.content`.
- **A page saved in two places at once.** A pending, content-less record pair (the browser extension's remote mode, or another device's URL-only save) can already be in iCloud when this device saves the same page. Its first upload, save-if-new, then finds the records there (`serverRecordChanged`, now returned by `CloudKitZone.saveIfNew`). iCloud's copy is merged into the article here (`CloudKitArticlesZoneDelegate.mergeICloudCopies`, articles still stored here only, so one deleted meanwhile isn't brought back): its title, address and saved date replace the local ones, and a local body, excerpt, image and byline are kept when the copy has none. If the copy has no body and this device has one, the body goes up as `.content` in the same send run; a copy that already has a body stays (the first body in iCloud wins, so Reset iCloud Sync can't overwrite newer bodies everywhere, and an anonymous extraction that gets there first beats a later Safari or Shortcut capture). First uploads iCloud refuses for another reason (storage full) are queued again after the run. On receipt, a record without a body doesn't replace a local body while this device has a pending `.new` or `.content` for it (`ArticlesTable.update`'s `keepingContentOf`, in the write's transaction); with nothing pending, the record wins, so a page deleted and saved again elsewhere starts fresh.
- **Saved dates.** Pages saved in the apps before 2026-10-12 had no `datePublished`, so each device showed when it received them (a new device: its install time for all of them). After the first successful fetch of each launch (`refreshArticleStatus`, which the Mac's timer sync and every full refresh go through), a device offers the time each page arrived here for a page with no saved date or one whose saved date is more than a minute later (`Account.savedDateProposals`, one SQL query). It reads those Article records' `datePublished` from iCloud, keeps iCloud's date when it's at most a minute later, and otherwise writes its own with save-if-unchanged, so a date another device wrote meanwhile isn't overwritten (`CloudKitArticlesZone.SavedDatePlan`, `CloudKitAccountDelegate.settleSavedDatesIfNeeded`); an article iCloud has no record of keeps the offered date here. Every device thus converges on the earliest time any device had a page; a page saved since carries its save time, which is never later than its arrival anywhere, so it's never offered. Known: a page deleted and saved again before another device saw the delete can get its first date back from that device.
- **The kick.** Saving, updating content and deleting call `storeAndSendArticleChanges`, which clears the no-change backoff and sends immediately; otherwise a save could wait 30 minutes.
- **Change tokens** live in `UserDefaults.standard` (`cloudkit.server.token.<zone>.<owner>`) and survive database wipes. Reset iCloud Sync (Mac app menu, iOS Settings > Troubleshooting) clears them and re-runs the first-launch sequence. If iCloud data is deleted, local data is kept and re-uploaded.
- **First launch:** find or create the account record, then save the feed record once per install, then fetch, then subscribe to both zones (once per install).
- **Unsigned builds** (tests) trap when they create a `CKContainer`, so the container and zones are created lazily and never under unit tests.

## iCloud on the web

The CloudKit framework only ever uses the iCloud account macOS is signed in to, and a managed work Mac can't be signed in to the user's. So the Mac app has a second way to reach the same private database: CloudKit Web Services (REST), with an Apple ID sign-in that belongs to the app alone. The browser extension's remote mode uses the same service. Nothing here has run against real iCloud yet: it was built from Apple's documentation, CloudKit JS and other clients' reports, and tested against a fake server that encodes them (`build/WebSyncTestSuite/`, not committed; see Plan.md, 2026-10-13).

- **Which way.** `CloudKitWebSync.isEnabled`: Info.plist `NetNewsListICloudTransport` = `web` (the work build, `scripts/build-work-mac.sh`), or a `-NetNewsListICloudTransport web` launch argument on any build (sign in with the same Apple Account the Mac's own iCloud uses: the different-account check below only knows earlier web sign-ins). Everything else is unchanged: the zones, their delegates, the sync database and the UI run the same code. `CloudKitAccountDelegate` gives the zones a `CloudKitWebDatabase` instead of a CKContainer (never created in this mode; the work build has no iCloud entitlement, so creating one would crash), and each `CloudKitZone` operation hands over to its counterpart in `CloudKitZone+Web.swift`. iOS never uses it.
- **Sign-in.** NetNewsList menu › Sign In to iCloud… (shown only in this mode, and opened at launch while signed out) loads Apple's sign-in page, fetched fresh each time the window opens, in a web view with its own persistent website data store (`ICloudSignInWindowController`). The page ends by sending the browser to the API token's sign-in callback with the token in `ckWebAuthToken` (and again in `ckSession`); the window cancels that navigation, so the token never reaches the callback host. `CloudKitWebService.verifySignIn` spends it at once on `users/current` (tried twice on a network hiccup) without storing anything; `CloudKitWebSync.completeSignIn` then compares the account with the last web sign-in's (`CloudKitWebUserRecordName`) and, for a different Apple Account, asks before `adopt` stores it. A failed sign-in doesn't navigate: Apple's page posts to `window.opener`, so a script stands in for one and forwards the message (`accessError` means web access to iCloud data is off, as Advanced Data Protection forces). The API token and environment come from Info.plist `CloudKitAPIToken`/`CloudKitEnvironment`, which the work build fills from the git-ignored `chrome-extension/local-config.json`; a build without one asks for it at sign-in, keeps it in user defaults, and asks again if iCloud refuses it.
- **The token** is good for one request (`X-Apple-CloudKit-Web-Auth-Token` on each response carries the next), so `CloudKitWebService` (an actor) sends one request at a time and stores each replacement in the login keychain (`KeychainWebAuthTokenStore`, with a copy in memory), but only while the stored token is still the one the request used, so a sign-out or new sign-in during a request stays. `CloudKitWebSync.isSignedIn` reads the store, which the service updates before it posts `CloudKitWebSignInDidChange`. iCloud ends a sign-in with AUTHENTICATION_REQUIRED/FAILED, or ACCESS_DENIED for the private database (web access turned off, or Advanced Data Protection on: `webAccessDisabled`); the post then carries `endedByICloud`, and the app shows a notification that opens the sign-in. A bare 421 is HTTP/2's Misdirected Request and is retried. "Keep me signed in" makes a sign-in last about two weeks (30 minutes without). While signed out nothing is sent; signing in syncs at once, and runs the first-launch setup if it never ran.
- **No pushes.** There are no subscriptions over the web, so the 30-minute quiet-period backoff is off and `ArticleStatusSyncTimer` keeps its 2-minute cadence: one `changes/zone` request every two minutes when nothing changed.
- **Mapping.** `CloudKitWebDatabase` turns requests and answers into CKRecords and CKErrors (`CloudKitWebRecordCoder`), so retries, zone creation and conflict handling work as before. A `.changedKeys` save is `forceUpdate` with the record's `changedKeys()` (fields left out stay as they are in iCloud, which is what keeps a saved date safe); save-if-new is `create`, or `update` with the change tag for a record fetched earlier (`CloudKitWebChangeTags` remembers tags per CKRecord object, since a CKRecord made here can't carry one); deletes are `forceDelete`. A save that finds iCloud's copy (`EXISTS`/`CONFLICT`) gets that copy as its `serverRecord` through small, retried lookups; when the copy can't be fetched, the save is reported as failed, not as a conflict, so it goes again later instead of uploading over the copy. Responses don't echo fields (`desiredKeys: []`). Requests carry at most 200 operations and about 2 MB, and a request iCloud refuses as too big (or as invalid) is halved until each record gets its own answer. An atomic request refused without a culprit, or failed only by deleting a record already gone, goes again without it or record by record; a record iCloud's answer doesn't mention counts as not saved.
- **Things the REST API does differently.** Deletions in `changes/zone` come without a record type: the Articles zone infers it from the name (`s|`, `a|`); the Account zone's deletions are ignored (NetNewsList never deletes those records). A fetch without a sync token lists the zone's whole history, deletions from long ago included; an article whose first upload is still pending here survives a deletion (both ways in, `CloudKitArticlesZoneDelegate.delete`), so saving a page again before the first sync isn't undone. There's no expired-token error: a sync token iCloud no longer takes comes back as `BAD_REQUEST`, which refetches the zone from the start once. There's no "user deleted the zone": a missing zone is recreated. Clearing a field (`{"value": null}`) isn't documented: if iCloud refuses it, the save goes again without clearing, leaving a stale value rather than saving nothing. If iCloud instead ignores it silently, the one visible effect is rare: a body replaced by one too big to stay inline (Retry with Live Page on a very long page) keeps the old inline copy, which readers prefer to the asset. Assets upload to the address `assets/upload` returns and download from the record's `downloadURL` on a separate URL session; a download refused for good is tried once more through a lookup (a fresh address), then that record is skipped until it next changes, never handed on without its body. iCloud can ask to wait for hours, in a refused answer or inside one that worked; past a minute, requests fail at once until then and the next timer run tries again.
- **Change tokens** are CloudKit Web Services sync tokens, kept under `cloudkit.web.token.<zone>.<owner>`, apart from the framework's, so a copy switched between the two never hands one a token from the other. Reset iCloud Sync clears both.
- **Limits.** Advanced Data Protection must stay off (no web token can be issued with it on, and a token issued before turns into `ACCESS_DENIED`). In August–October 2026 some developers reported web sign-in tokens refused with 421 for reasons on Apple's side; nothing in the app can work around that.

## Saving and extraction

- **Ingress.** Every way in ends at `ExtractionCoordinator.saveArticle(url:title:body:)`: the Add Article sheet, `netnewslist://add` (`netnewslist-dev://add` for the Mac Debug build, NetNewsList Dev, so links reach the installed app; Mac: `AppDelegate+URLHandling`, which returns focus to the browser; iOS: `SceneDelegate`), the `SaveArticleIntent` App Intent (runs in the app, may run in the background), dropped links (`DroppedWebPages`, Mac), the Services menu item "Save to NetNewsList" (Mac, `SavePageService`, `NSServices` in Info.plist: a selected link or address, or every web address in selected text; it shows only when the selection contains one), and the share extensions. Extensions can't use iCloud or run extraction, so they write a `SavedArticleRequest` property list into `<app group>/Inbox/` (one file per request) and `SavedArticleRequestProcessor` saves them at launch, on new files, on foreground and in the iOS background refresh. The browser extension's remote mode writes the two iCloud records directly (see `chrome-extension/README.md`).
- **Extraction** (`Modules/Extraction`, driven by `Shared/Extraction/ExtractionCoordinator`): `PageFetcher` does one GET in a fresh ephemeral session (browser user agent, 20 s, 5 MB, HTML only, charset from the header, `<meta>` or UTF-8). **Don't use RSWeb's `Downloader` for this**: it caches error responses, so Retry would get the same failure. `ReadabilityWebExtractor` keeps one hidden `WKWebView` with page JavaScript off and runs Readability.js 0.6.0 and DOMPurify 3.4.16 in an isolated content world on a `DOMParser` document, which never runs the page's scripts or loads its resources. "Retry with Live Page" loads the real page with JavaScript on, waits 1.5 s and extracts the rendered DOM. A body under 100 characters counts as a failure.
- **Who extracts.** The device that saved the page, at once; and any device that sees a pending article (on launch, foreground and after each iCloud fetch). A local `ExtractionLedger` (JSON in the account folder, never synced) records failures and allows three automatic attempts (immediately, after 1 minute, after 10 minutes), then waits for Retry. Extraction runs only in the foreground: on iOS it pauses when the app goes to the background.
- **Stored content never runs scripts.** The article view sets `allowsContentJavaScript = false` for stored bodies. Neither app shows a live page itself: Open in Browser and links tapped in an article go to the system browser. The only web pages the apps load are the hidden extractor's (Retry with Live Page, X posts) and X's sign-in page.

## X posts

- **Links.** `URLCanonicalizer` turns a link to an X post on any X host (`x.com`, `twitter.com`, their `www.`/`mobile.` forms, the `fxtwitter`/`vxtwitter`/`fixupx`/`fixvx` mirrors), with any screen name, `/photo/N` suffix or `?s=…&t=…` share parameters, into `https://x.com/i/status/<id>`; the JavaScript canonicalizer does the same (shared vectors). `URLCanonicalizer.xPage(for:)` says whether a link is an X post or an X Article (`/<user>/article/<id>`, `/i/article/<id>`).
- **Extraction.** X's static page is a sign-in wall for everyone, and Readability used to save it as the post. X pages are always read live: `ReadabilityWebExtractor.extractXPage` loads the post at `https://x.com/i/status/<id>` (no redirects) with X's scripts on and a 30 s limit, waits for `netNewsListX.state` (`x.js`) to report the post, then `netNewsListX.extract` rebuilds it as plain HTML: the post and the author's posts directly before and after it (a thread), text with links and line breaks, photos at `name=large`, video posters linked to the post, quoted posts as blockquotes; for an Article (`.x-article-body` inside the post), the cover, title and body blocks with embedded posts as quotes. A post can be one word or just a photo, so X pages skip the 100-character minimum. A body supplied by a share (Safari's Readability capture) is ignored for X links.
- **X's two pages.** X serves different web clients, and `x.js` reads both. Signed out, a newer server-rendered client with utility class names and no `data-testid`s: `<article>` per post (a quoted post is a nested `<article>`), the status link `/<handle>/status/<id>` next to an inline script that carries the timestamp, a `dir="auto"` text block, `pbs.twimg.com/media` images and `.x-article-body`; a copy of the shared post comes first and the conversation follows (hidden), so each post's last occurrence wins. Signed in, the classic client: `article[data-testid="tweet"]`, `tweetText`, `User-Name`, `tweetPhoto`, `time[datetime]` inside the post's link, a quoted post in a `div[role="link"]`, a `tweet-text-show-more-link` on cut-off posts, and Articles in `article[data-testid="twitterArticleReadView"]` (`twitter-article-title`, Draft.js blocks in `longformRichTextComponent`). It renders the shared post first and adds the conversation and an Article's embedded posts afterwards, so the extractor polls `netNewsListX.signature()` until the page stops changing (a second, at most 6 s), in a 4000-point-tall web view, and starts polling as soon as the page loads rather than after every image. When X changes its pages, check signed out with `Tools/extract-page`, and signed in in the app.
- **Sign-in.** `XAccount` keeps the user's X session in a persistent `WKWebsiteDataStore(forIdentifier:)` of its own, on this device only; the extractor and the sign-in screen (Mac: NetNewsList menu > Sign In to X…; iPhone: Settings > Articles > X Account) share it, and signing out removes its data. Signed-in state is the `auth_token` cookie. Signing in retries pending X pages. Signed out, posts, long posts, threads and Articles were all readable on 2026-10-11; a page that shows only X's sign-in wall fails with `ExtractionError.signInRequired`.

## Offline images

The stored HTML keeps the original image URLs. When an article is shown, `ArticleImageRewriter` points each `<img>` at `nnlasset://<articleID>/<base64url(original URL)>` and drops `srcset`; `ArticleAssetSchemeHandler` serves the copy from `ArticleAssetStore` (`Application Support/NetNewsList/ArticleAssets/<articleID>/<sha256(url)>`, not backed up, not synced), downloading it if missing and showing a placeholder if that fails. `ArticleAssetCoordinator` downloads an article's images when it gets a body (40 images, 25 MB per article, 1600 px), deletes them with the article, and tidies orphans at launch. Don't put them in `Caches`: `CacheCleaner` empties `Caches/Images` every three days.

## Backups

iCloud sync isn't a backup: the Mac, the iPhone and iCloud mirror each other, so a mistaken delete, a sync bug or a Retry that replaces good text with a paywall teaser reaches every copy within a minute. This Mac has no Time Machine, and the iCloud data lives in CloudKit's Development environment. So the Mac app keeps its own snapshots: `ReadingListBackups` (Mac only) writes `Application Support/NetNewsList/Backups/NetNewsList <yyyy-MM-dd HH.mm.ss>.json` in the app's container at launch and then once a day (checked hourly against the clock, so sleep counts), skips the write when the newest snapshot has the same bytes, and keeps the newest 30. File > Show Backups in Finder reveals them. The JSON (`Account.readingListBackupData()`, `formatVersion` 1) lists every article, Queue and Archive, oldest first: `articleID`, `url` (canonical), `externalURL`, `title`, `contentHTML` (null = not extracted yet), `summary`, `imageURL`, `authors`, `dateSaved` (`datePublished ?? dateModified ?? dateArrived`, ISO 8601) and `isArchived`. Images aren't included; they're downloaded again from their original addresses. There is no Restore command: if one is ever needed, it's a one-off like the Matter import (Plan.md, 2026-10-11): put back the articles that are missing, with `dateSaved` as `datePublished` and `isArchived` as read, and upload them.

## Interface

Pared down on 2026-10-11 (Plan.md has the details). Both apps open on the Queue at every launch; the Archive is secondary. On iOS the Queue is the root screen, with "…" (a menu: Archive, Settings) on the left and "+" (Add Article) on the right; Archive pushes onto the same stack; tapping a row pushes the article, whose top bar has Archive / Move to Queue, Open in Browser and Share (Find in Article and Open in Browser are in the share sheet). The iPad shows the list and the article side by side. The Mac window has two panes, the list and the article; the toolbar has "+" and the "…" menu (Queue ⌘1, Archive ⌘2, also in the Go menu) over the list, and Archive / Move to Queue and Open in Browser over the article; the window title says which list is showing. Gone from both: the sidebar, search, Archive All, in-app browsing (Show Original), article themes (only the built-in Default), full-screen articles, Group by Site and the timeline layout setting (rows on both are one line of title with a small icon, and the site and date below), the appearance setting (both follow the system), Help/About on iOS and the Mac Preferences window. iOS Settings keeps Sort Oldest to Newest, X Account and Troubleshooting. Archive and Move to Queue use `archivebox` and `tray.and.arrow.up` everywhere.

## Traps

- `articles natural join statuses` is how every query reads articles: never add a column with the same name to both tables.
- `SidebarItemIdentifier` values still travel in Handoff activities (`sidebarItemID`) and may be in old saved state; unknown ones are ignored, not asserted. Neither app saves which list was showing: both open on the Queue.
- The keyboard-shortcut plists in `Shared/Resources/` are loaded by both apps; an entry removed for one app is gone from the other too.
- `main.js`'s `convertImgSrc` leaves `scheme://` sources alone; that is what lets `nnlasset://` work.
- The Xcode project uses file-system-synchronized groups: a new file under `Mac/`, `iOS/` or `Shared/` is in the app targets automatically; extension targets compile only the files listed in their exception sets in `project.pbxproj`. Build settings belong in `xcconfig/`; a build phase fails the Mac build if the project file gains any.
- The Mac app group is Team-ID-prefixed (`<team>.<org>.NetNewsList`), the iOS one is `group.<org>.NetNewsList.iOS`; the `AppGroup` Info.plist key must match the entitlements or extensions can't reach the inbox.
- The browser extension's CloudKit API token is per environment (Development for Xcode builds, Production after the schema is deployed) and isn't committed (the repository is public); it goes in the extension's options or a git-ignored `chrome-extension/local-config.json`. Each web auth token is good for one request; the replacement comes back in the `X-Apple-CloudKit-Web-Auth-Token` response header. The sign-in callback is matched by exact origin, and the token it carries is spent at once (a `users/current` check), because the browser sends it to the callback host before the tab closes. Advanced Data Protection must stay off for web sign-in to work.
